Inflozo PRD v2.1 — Validation Report

_bmad-output/planning-artifacts/prds/prd-Inflozo-2026-08-17/prd.md
Poor

This is an unusually decision-dense, testable PRD: nearly every FR carries a verifiable consequence, trade-offs are recorded with what was given up (Addendum AD3, Appendix G, FR-J14's "chosen for implementation simplicity"), and the appendices are genuinely normative rather than decorative. What's at risk is the handoff layer, not the substance: there is no glossary and no user journeys for a product whose thesis is experience quality, so the UX agent must reconstruct flows from FR prose — and one real coherence gap (every starter emits routes.yaml, putting the manual Ghost Admin step into every starter first deploy) could ship unexamined into onboarding design.

The adversarial and consistency reviewers materially shift that picture, and they drive the grade. Two critical findings make the PRD unsafe to hand to autonomous agents as-is: FR-J14 promises updates arrive "never automatically" while mandating a single unpinned live library, so every redeploy is a compulsory upgrade the user cannot decline; and FR-D6's "documented synthesis defaults" — the mechanism a home-only design depends on to produce a complete theme — are documented nowhere. Around them sits a cluster of asserted-but-unavailable third-party mechanisms (theme download via an Admin API endpoint Ghost doesn't document, Ghost(Pro) plan detection no API exposes), an unsatisfiable Definition of Done (deploy to T4, a target that blocks deploys by design), and stale companion-file residue from the same-day hardening pass. The grade is Poor by the rubric's formula (any critical finding); the substance underneath grades strong, and each critical is a one-paragraph decision away from resolution — this is a hardening problem, not a rethink.

Decision-readiness

strong

Decisions are stated as decisions, with force. The §5 preamble even explains its own ordering. Real trade-offs name their cost: FR-J14 picks a single live library "chosen for implementation simplicity" and immediately owns the consequence; FR-D10/AD1 accept a data-loss window and say so; §4's live-production testing is labeled "owner mandate — must-have" with an explicit safety argument rather than smoothed into neutrality. AD3's rejected-alternatives log is exactly what this dimension asks for. Counter-metrics on G8–G10 show the metrics were argued, not listed. Zero Open Questions on a status: final PRD is earned here, not evasive — the residue of debate is visibly recorded.

medium

No contingency for the all-or-nothing library bet

§4 P7, G5, §7.6
"Everything ships before launch" plus 487 variants is the PRD's biggest schedule risk; §7.6 names it but the mitigation is only "factory workflow + shared primitives". There is no de-scope trigger: if Wave 3 (E11) slips, is launch delayed, or is there a smaller normative floor?
Fix: One sentence in §4 stating the fallback (even "launch slips; the 487 inventory is not de-scopeable" is a decision worth writing down).

Substance over theater

strong

Nothing here is furniture. The four personas (§3) are lean and each one is traceable to real scope. The Differentiators (§1.4) each resolve to named FRs rather than adjectives, and §1.5 names the competitor's specific gaps instead of generic superiority claims. NFRs carry product-specific numbers throughout (theme JS < 30 KB gzipped; 60/80/95% quota alerts; Safari 16.4+). The vision's one unfalsifiable flourish ("the most beautiful UI/UX in the Ghost ecosystem") is operationalized by G6 and Appendix H, so it reads as ambition, not theater. No findings.

Strategic coherence

strong

The thesis is crisp and everything hangs off it: single-source WYSIWYG (P4/§7.3, enforced to the point of rejecting React previews by fiat), impossible-to-make-ugly (P2 + closed control vocabulary + token-only sections), and Ghost-native depth (FR-H6, FR-Q, A32) as the moat against Fantasma. Success metrics validate the thesis rather than counting activity, each with a counter-metric. MVP scope kind is coherent — a deliberate full-product experience-plus-revenue GA, with §4 explaining why that's safe. One coherence gap, and it's the most consequential rubric finding:

high

Every starter forces the manual routes.yaml step into first deploy, unreconciled with G2 and the ease thesis

Appendix E, FR-I1, FR-I4, FR-I5
Appendix E declares all 10 starters ship with "Members … designed"; FR-I1 says designing a members template "automatically adds its route … to routes.yaml"; FR-I5 confirms "designing one is, in effect, opening routing." Therefore every starter-created project (and every FR-C7 redesign proposal) emits routes.yaml — and FR-I4's guided manual Ghost Admin → Labs upload is "the primary, documented flow." The flagship onboarding path always lands the "one more step" card on the user's very first deploy — the moment Appendix H reserves for confetti — and the PRD never acknowledges this tension against G2's "< 15 minutes" or "extremely easy." Downstream UX will design first-deploy celebration without knowing the interruption is unconditional.
Fix: Decide and state it — either starters ship with members templates present-but-undesigned (Ghost Portal covers those flows natively, no routes.yaml emitted), or the "one more step" card is explicitly designed as part of the first-deploy journey and §4/FR-O1 say so.

Done-ness clarity

strong

This is the PRD's standout dimension. FRs routinely specify the failure paths and edge lifecycles that PRDs usually leave to discovery: FR-H2 defines the zero-feed-section SEO guard and the main-feed designation lifecycle; FR-J13 pins snapshot semantics down to "never re-captured while the active theme is an inflozo-* theme"; FR-L2 enumerates the full entitlement transition table; FR-C7 makes variety an explicit acceptance criterion. "Gracefully" appears, but almost always immediately defined. NFR-6 gives downstream QA a concrete four-part gate.

Adversarial review

review-adversarial-general.md

Verdict: This is a strong v2.1 — most of the classic PRD failure modes are already patched — but it is not safe to hand to autonomous agents yet. Two requirements are unbuildable or self-contradictory as written (forced library updates sold as opt-in; compiler "synthesis defaults" that are documented nowhere), the flagship "safe installs" promise rests on an Admin API endpoint Ghost does not document, and the business model's own math invites export-and-cancel. The document's confidence is its biggest liability: it states mechanisms ("detect custom-theme capability", "tracks the last routes.yaml delivered") that no public Ghost API supports, and downstream agents will either invent them or build theater. Minimum bar before handing downstream: resolve C1 and C2, and settle H1–H5 (each is a one-paragraph decision); the metrics FR (H7) must exist before the SM writes stories. 2 critical · 8 high · 13 medium · 6 low = 29 findings.

critical

C1 · Library updates are compulsory while being sold as opt-in — FR-J14 contradicts itself

FR-J14; §1.4 diff 5 & 7; AD3
"The user updates by redeploying — never automatically" vs., two sentences later, "Compiles always use the current library version (a single live library, no per-project pinning)." These cannot both be true. With no pinning, every redeploy is an automatic, involuntary, full library upgrade. A user who redeploys to fix one line of copy silently absorbs every section change since their last deploy. The "Updates available" notice is decoration: the user has no way to decline. This also detonates differentiator 5 ("an Inflozo theme never breaks your site"): a library regression ships to user sites piggybacked on unrelated edits, and the only escape (rollback) throws away the edit the user was trying to make. Downstream agents will build both halves faithfully and ship a product that lies to its users.
Fix: Pick one. Either (a) pin each project to its last-deployed library version with an explicit "Upgrade library" action (reverse AD3), or (b) delete "never automatically," reword differentiator 7, and add a pre-deploy diff summary + mandatory confirmation whenever the library advanced, plus render-matrix evidence that placed variants are visually unchanged.
critical

C2 · "Documented synthesis defaults" are documented nowhere — the compiler's behavior for untouched templates is pure invention

FR-D6; FR-I1; §7.4
"Derive header/footer/style" covers three of the ~10 decisions per template. A blank-canvas user designs Home only; the compiler must then emit post/page/tag/author/error templates — which post header variant? Which content layout? Related posts or not? Which pagination style? Appendix A inventories 487 variants but defines zero default compositions; nothing supplies the recipe. The word "documented" points at a document that does not exist. Three downstream agents will produce three different default themes, and the one thing G2 (<15 min to first deploy) depends on is unspecified at its core.
Fix: A normative appendix (or a section in sections-inventory.md): per template, the exact default section stack (category + variant id + key control values) and the derivation rules from the Home canvas. One page of tables.
high

H1 · The "safe installs" snapshot depends on an Admin API capability Ghost does not document

FR-J13; §1.4 diff 5; P8
Ghost's documented Admin API for themes is upload and activate; theme download is an internal endpoint. Whether a Custom Integration JWT can call it — on self-hosted 5.x, 6.x, and especially Ghost(Pro) — is unverified. FR-I4 hedges the routes endpoint as "community-known internal" with a first-class manual fallback; FR-J13 gets no such treatment. The warn-and-proceed fallback firing on 100% of Ghost(Pro) connections would gut the differentiator at launch.
Fix: Same treatment as FR-I4: name the endpoint as internal/undocumented, require verification per Ghost version/host as an acceptance criterion on all four §4 targets, and specify the degraded path as a designed flow, not a warning toast.
high

H2 · Ghost(Pro) Starter "capability detection" has no mechanism — no API exposes it

FR-C2; FR-C5; §7.6
Ghost has no endpoint that reports plan or theme-upload permission; the site/settings reads FR-C2 specifies return neither. The only reliable probe is attempting a theme upload — a side-effecting action P8 forbids outside deploys. The architect must invent: hostname heuristic, probe upload + delete (violates P8's spirit), or flag-on-first-failed-deploy (contradicts "deploy attempts are blocked").
Fix: Choose the mechanism: connect-time heuristic (Ghost(Pro) hostname + documented lookup) with the authoritative signal being the first deploy attempt's error response; rewrite FR-C2/C5 accordingly.
high

H3 · Theme-name freeze vs. collision-rename is a deadlock, and the freeze's scope is ambiguous

FR-J10; FR-B5
"First deploy to a site" — first deploy ever, or first deploy to each site? FR-B5 makes projects site-switchable: project first-deploys to Site 1 (name freezes), switches to Site 2 where another inflozo-blog lives. Collision → "prompts a project rename" → but renaming "changes the display name only" because the theme name is frozen. The prompt asks for an action the same FR defines as a no-op; deploy to Site 2 is permanently blocked.
Fix: Freeze per project×site (each site gets its own frozen slug, collision resolved by a per-site slug suffix), and say so explicitly.
high

H4 · Tag and author archives are excluded from the main-feed rule — broken pagination on every archive page

FR-H2; FR-D6; Appendix A §29, §34
Ghost paginates taxonomy pages (/tag/x/page/2/) with the same native pagination context as collections, but FR-H2's designation rule scopes itself to "index and custom collections" — so on archive templates every feed section is {{#get}}-driven with a fixed Count, meaning page 2 of every tag archive renders the same posts as page 1. That is precisely the indexable-duplicate failure FR-H2 guards against for zero-feed collections, silently reintroduced on every archive of every theme.
Fix: Extend the main-feed designation and lifecycle to all paginated contexts: index, custom collections, tag, and author templates.
high

H5 · FR-Q5's "its dark counterpart already exists" is false for every token except accent

FR-Q5; FR-Q3; FR-Q2
The built-ins reserve exactly one dark color: Dark accent. Promote surface, background, or text and no dark counterpart exists. The architect faces an undecided fork: auto-create a dark twin (consuming two of the 17 user slots per promotion, wrecking the cap arithmetic) or promote light-only (shipping the exact broken half-pair FR-Q5 claims cannot happen).
Fix: Decide: color promotion creates a light+dark pair costing 2 slots (meter shows it), or promotion is accent-only in v1, or dark values always derive from light via the pack's pairing rules. One sentence.
high

H6 · Edit-lock takeover destroys work with unspecified semantics — and the undo stack survives a doc it no longer matches

FR-D18; FR-D10; FR-D9; AD1/AD2
(1) The former holder's unsynced ops: "not included" — destroyed, recoverable, or merged later? The local journal still physically contains them; when that device re-acquires the lock and the doc is replaced by the cloud snapshot, do its orphaned ops vanish, replay, or linger as landmines in the undo stack? Up to 3 minutes of work (unbounded with autosave off) is at stake. (2) FR-D9 protects undo only against schema mismatches, not doc-state mismatches: after hydrate-from-cloud, every persisted undo entry references a document that no longer exists.
Fix: Specify: on hydrate-from-authoritative-snapshot the local undo journal is cleared (or archived as a read-only "recovered edits" bundle); takeover UX states the loss in edits, not vibes. AD1/AD2 get one paragraph each.
high

H7 · G8–G10 are unmeasurable — no FR builds the instrumentation

§1.3 G8/G9/G10; NFR-8; §5
Activation funnels, 90-day conversion cohorts, monthly churn, rollback rates — all require event instrumentation and cohort reporting. No FR specifies any of it; the only mention of analytics is NFR-8's aside. Downstream agents build zero telemetry and the launch flies blind against its own goals. "7-day rollback rate" is also underdefined (per deploy, per user, per site?) and perverse — rollback is a headline safety feature.
Fix: An FR-R (analytics/telemetry): named events, the chosen privacy-respecting tool, dashboard requirements, and precise denominators for every goal and counter in §1.3.
high

H8 · The business model funds its own churn: export-and-cancel is the rational Pro behavior

Appendix F; FR-J12; FR-J15; P5; §1.5; G10
One month of Pro ($15) buys: build up to 25 themes from all 487 variants, export white-labeled, cancel. The themes work forever (P5 — correctly, but it removes the hostage). Inflozo is accidentally the cheapest one-shot theme tool on the market, while G10 assumes <5% monthly churn with no retention mechanic. Nothing addresses generated-theme licensing either — FR-N1's legal pages don't include theme license terms. Separately, §1.5 leans on unverifiable competitor claims stated as fact.
Fix: Either model one-shot economics honestly in Appendix F (blended LTV with a month-1 churn spike, which changes break-even), or add a stated retention mechanic (e.g., white-label export requires active subscription per Terms; theme license terms as a required legal page), and mark §1.5 claims with a verification date.

M1 · "Impossible to make ugly" and "Accessibility ≥ 95" are unenforceable the moment FR-E3 exists

§1.4 diff 4; G4; FR-G4; FR-E3
FR-G4 claims AA "via token pairs," but FR-E3 lets users edit every token to failing values with only a warning. AA and Lighthouse-a11y-95 are properties of the 12 presets, not of "every possible output" — yet G4 is written as a goal over generated themes, unqualified. QA agents will fail builds that are working as designed.
Fix: Scope G4/FR-G4 to preset packs and library defaults; state that user token edits can break AA and the warning transfers responsibility.

M2 · Goal measurements are undefined: G1's 60-second clock includes a manual Ghost Admin task

G1, G2, G6
FR-C1's connect flow requires the user to open Ghost Admin, create a Custom Integration, and paste two keys. No first-time human does that in 60 seconds — either the clock starts after key paste (unstated) or the goal is theater. G2 has no percentile; G6's "60fps" names no reference hardware.
Fix: Define each goal's clock start/stop, percentile, and measurement environment in §1.3.
medium

M3 · Unbounded performance promise: "no hard cap" + 60fps with no stated budget

FR-D14; NFR-1; G6; FR-F4; FR-E2
An unbounded input with a fixed performance floor is unfalsifiable, and "long pages" is not a number. The same interaction also has two budgets: G6 says control changes visible "< 100 ms," FR-F4 says "within one frame" (16 ms).
Fix: A tested reference budget ("60fps up to N sections; degradation strategy beyond N"), and one number per interaction.

M4 · "Routes never silently drift" is unverifiable — Inflozo cannot observe the manual upload

FR-I4
In the primary (manual) flow, "delivered" means "we showed the user a download button." Whether the user completed the Labs upload is unknowable, so the tracked state measures Inflozo's output, not Ghost's reality. A user who skips the step has drift the system believes impossible.
Fix: Rename the state honestly ("last routes.yaml offered"), add a verification probe where possible (fetch a route URL and check), with an "unverified" nag state.

M8 · Pre-Inflozo snapshot keyed by site URL — domains change

FR-J13

M9 · "Safety operations remain available throughout" — not for the sites you were forced to disconnect
