Decision-readiness

strong

Decisions are stated as decisions and attributed. §4 carries "No de-scope contingency (owner decision)" and "Live-infrastructure testing (owner mandate — must-have)"; FR-J8 carries "(owner requirement: 'deploy only' vs 'deploy and activate' are distinct buttons)"; FR-D4 carries "Every text prop is also editable in the Content group of the sidebar (owner requirement)". Trade-offs name the cost, not just the choice. FR-J14: "no per-project pinning — chosen for implementation simplicity); consequently any redeploy includes all library changes since the project's last deploy — there is no way to redeploy without them." FR-K2: "Optimization is destructive by design — originals are not retained." Appendix F volunteers the worst news in the document — "themes work forever and export stays open, so an export-and-cancel cohort is expected — model a month-1 churn spike honestly in blended LTV" — which is the opposite of a PRD smoothing everything to neutral.

Zero Open Questions, zero [NOTE FOR PM], zero [ASSUMPTION] tags is the correct end state for status:final at launch stakes, and here it is earned rather than achieved by erasure: §7.6's six-item "Verify at build time" list carries the residual uncertainty with a named re-verification trigger ("re-confirm each before the dependent epic starts"). Shape fit

strong

The shape matches the product. This is a chain-top PRD for a consumer-facing product with heavy UX weight, feeding Analyst → PM → Architect → SM → Dev → QA, and it invests where that shape demands: a normative glossary, a registry entry format (FR-G3) that is a literal downstream contract, a generated-theme file tree (§7.4), a data-model sketch (§7.5), and epic sequencing. It resists the two failure modes the rubric names. It is not over-formalized — 116 FRs against 487 library deliverables, a Handlebars compiler, a helper-emulation layer, a routing builder, a custom-settings builder, a translations module, and a billing state machine is FR density tracking real surface area, not ceremony; four personas is at the limit, not over it; there are no ceremonial sections. And it is not under-formalized despite having no user journeys, because the FRs carry behavioral detail at the level journeys usually supply.

On whether the journey delegation is safe: for build it is. Architect, SM, and Dev never need a journey document here — §5 plus the appendices plus addendum.md are sufficient to design and story-map the system, and the delegation is explicit, names its consumer, names its inputs (§3 personas), and names a floor. That is a real handoff contract rather than an omission dressed as one. The residual risk is entirely on the UX side and is captured in the Downstream finding above.

One shape note worth stating: this is greenfield code against a brownfield platform. Ghost's undocumented endpoints, plan lineup, and version behavior are the highest-variance dependencies in the build, and §7.6's "Verify at build time" list plus §4's four live targets are exactly the right instrument. That is a shape-aware choice, not a template artifact — and the external-claims pass is the proof of the diagnosis: five of that reviewer's nine contradictions land precisely on the platform surface §7.6 exists to police. The instrument is right; it was pointed at six items when it needed to be pointed at ten. No findings for this dimension.

F-1 · REGRESSED (H8) — the journal-clearing rule destroys FR-D9's persist-undo-across-reloads promise

prd.md:147 FR-D9; :148 FR-D10; :156 FR-D18; addendum.md AD1
FR-D9 makes two claims in the same paragraph: "The undo stack persists locally (per browser) across reloads and sessions … even after a reload" and "On any hydrate from the authoritative cloud snapshot (lock acquisition or takeover), the local undo journal is cleared." FR-D10 fixes the trigger unambiguously: "On every lock acquisition, the cloud snapshot is authoritative." A reload ends the editing context and opens a new one, therefore re-acquires the lock, therefore hydrates, therefore clears the journal — on every ordinary refresh, on the same device, with no second editor anywhere.
