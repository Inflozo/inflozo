## 1. Goals & Background Context

### 1.1 Problem

Ghost is a world-class publishing platform with a primitive theming story. Customizing a Ghost site means hand-editing Handlebars templates, working within a marketplace of rigid pre-built themes, or hiring a developer. Visual building for Ghost is barely served: the most prominent shipping visual Ghost builder, Fantasma, falls short on the axes that matter (see §1.5). Ghost publishers who care about design are still stuck choosing between "someone else's theme," a shallow builder, and "learn to code."

### 1.2 Product Vision

**Inflozo is the visual builder for Ghost CMS.** Users assemble their site by dropping pre-made, professionally designed sections onto a canvas that **renders exactly what Ghost will render** — the canvas is the page, not a preview of it. (The promise is scoped to what Inflozo emits: a user's own Ghost code injection legitimately changes the live page and is outside Inflozo's control, which is why connecting a site that carries code injection surfaces a notice.) Inflozo compiles the design into a clean, valid, marketplace-quality Ghost theme and deploys it to the user's site in one click. The experience must be **extremely easy, genuinely fun, and the most beautiful UI/UX in the Ghost ecosystem** — closer to playing with a well-made toy than operating software.

### 1.4 Differentiators

1. **Single-source WYSIWYG** — the canvas and the compiler consume the *same* section source: the canvas renders it directly, the compiler serializes it into the `.hbs` + CSS that ships in the theme. There is no second preview implementation to drift out of sync (§7.3).
2. **Variant Shuffle** — flip a placed section through every sibling design in its category (up to 18) with the user's content preserved. Choosing a design becomes play.
3. **Auto-branding** — on connect, Inflozo reads the site's accent color, logo, title, and navigation from Ghost and seeds the project so the first canvas already looks like *their* site.
4. **Impossible to make ugly** — a strict vertical-stack model, a **disciplined** control vocabulary with no raw CSS values (open to new control types when a section genuinely needs one, never to raw values — FR-F1, Appendix C), and token-driven Style Packs mean every possible output is cohesive.
5. **Safe installs** — "an Inflozo theme never breaks your site" is a brand promise enforced in the pipeline: gscan-gated compiles, pre-deploy checks, a **pre-Inflozo snapshot** of the site's previous theme captured at Inflozo's first theme *upload* to that site (deploy-only included — never activation-time, FR-J13), a pre-deploy confirmation that the user holds their own copy of the current theme and routes file, **drift detection** that halts any deploy which would overwrite theme changes Inflozo did not make, and one-click rollback (FR-J6, FR-J9, FR-J13). Capture is real, not best-effort: Inflozo reads the live theme with the site Owner's **Staff Access Token**, which is not bound by the method allowlist Ghost applies to Custom Integration keys — that allowlist blocks every `GET /themes/*` call made with an integration key, on every version and every host.
6. **Deep Ghost nativity** — live tiers pricing, members-aware sections, paywall CTA designs, Koenig card styling, portal actions, routes.yaml building. Inflozo is not a generic builder wearing a Ghost costume.
7. **Evergreen themes** — the section library is versioned and updated as Ghost evolves; users pick up improvements by signing in and redeploying (FR-J14). Competing themes are frozen at purchase time.

### 1.5 Competitive Landscape

**As of August 2026**, Fantasma (fantasma.io, Pro $99/yr) is the most prominent shipping visual Ghost builder. Its public product material describes form-based sidebar editing (no inline WYSIWYG), 155+ presets, and — on Pro — **direct publishing to Ghost** via an Admin API key with connected-site preview. Absent from that material, and central to Inflozo: membership and monetization sections (tiers, paywall designs), deploy versioning and rollback, image optimization, and any gscan or code-quality story. Ghost theme shops sell static themes at **$35–149 one-time (most $69–99)**. Inflozo's premium $15/mo is justified against both by WYSIWYG fidelity, library scale (485 variants at GA), Ghost-native monetization depth, safe installs, and evergreen updates.

Every competitor statement above is a **dated observation, not a standing fact**. Any competitor claim reused on the marketing site (FR-N1, FR-N3) must be re-verified against that competitor's live public material at publish time and carry its verification date; an unverified comparative claim does not ship.

## 2. Product Principles (binding on all design & implementation decisions)

- **P1 — The canvas is sacred.** With nothing selected, the canvas shows the true website: no outlines, handles, grids, or badges. Affordances appear only on hover/selection and vanish on exit.
- **P2 — No CSS knowledge, ever.** Users never see pixels, hex codes, class names, or units at the section level. All values are named (Compact/Comfortable/Spacious), visual (layout thumbnails, swatches), or binary (toggles). The control vocabulary is **disciplined, not closed** — it may grow when a section genuinely needs a new control type (FR-F1, Appendix C) — but it never admits a raw value at the section level. Raw values exist in exactly one place: the Style Pack editor.
- **P3 — Bake by default, expose deliberately.** Section copy and control values are compiled into the theme. The generated theme exposes `@custom` settings only where the user deliberately configures them in the Theme Settings surface (FR-Q): the dark-mode built-ins (FR-Q5) plus any user-defined custom settings — always within Ghost's 20-setting cap, enforced with a visible meter.
- **P4 — One source of truth per section.** A section is its **annotated HTML** source + CSS (+ optional JS). The editor renders that source directly; the compiler serializes the same source into the theme's `.hbs`. No parallel React re-implementations of sections, and no second copy of a section anywhere.
- **P5 — Deployed sites cost Inflozo $0.** Assets bundle into the theme zip and are served by the user's Ghost server. Ghost content loads in the editor client-side via the Content API (which is designed to be browser-safe and cacheable). Inflozo's infra pays only for editing sessions and the marketing site.
- **P6 — Delight in small doses.** Micro-interactions, playful copy, and one celebratory moment (first deploy) — never at the expense of speed or clarity.
- **P7 — Everything ships before launch.** The full library, all templates, all plans, all pages. Testing happens on the production Vercel + Supabase stack against real Ghost instances (there are no users yet; see §4 — "Live" names the post-launch environment, not this one).
- **P8 — Ghost content is read-only.** Inflozo never creates, modifies, or deletes the user's Ghost content (posts, pages, tags, authors, tiers, settings). Deleting a section removes theme code from the project only. The Admin API is used solely for connection validation, theme upload/activate, reading the live `routes.yaml` to verify the user's guided upload (FR-I4), and reading the live theme for the **pre-Inflozo snapshot** and pre-deploy drift check (FR-J13).

## 3. Users & Roles

**One user role.** Every account has identical capabilities, differentiated only by plan (Free/Pro).

Personas (for tone and for the UX workflow, not permissions — no requirement is prioritized by persona):
- **The solo publisher** — writer/newsletter operator on Ghost; zero code skills; wants their site to look intentional. Primary persona.
- **The indie founder** — runs a company blog/changelog on Ghost; wants a marketing-grade homepage without a designer.
- **The creator with taste** — designer-adjacent; will use custom Style Pack editing, dark mode authoring, and routes.
- **The multi-site operator** — manages several Ghost sites (Pro; up to 10 connections, 25 projects).

An internal `admin` claim (Supabase custom claim, not a product role) gates suggestions-board moderation and support tooling.

## 4. Release Strategy & Definition of Done

- **Single GA release.** No beta, no waitlist-gated feature drip. 100% of this PRD ships before go-live.
- **Production-infrastructure testing (pre-launch)** — owner mandate, must-have. Until go-live and the first customer, all testing runs on the real production infrastructure, exactly as an actual user would experience it: the production domains (**inflozo.com** marketing, **app.inflozo.com** app), production Supabase, real Resend sends, real Dodo transactions (test-mode → live-mode), plus real Ghost deploy targets. ("Live" is reserved for the post-launch environment below; these are Ghost *deploy targets*, not the Live environment.)
  - **T1** — a self-hosted Ghost **6.x** on a DigitalOcean droplet (owner-provided)
  - **T2** — a Ghost(Pro) **Publisher** site
  - **T3** — a self-hosted Ghost **5.x** droplet (owner-provided), retained as a **compatibility** target for lagging sites and the **first candidate to drop under schedule pressure**: Ghost 5.x reached end of life in January 2026, so 5.x parity is a courtesy, not a permanent commitment (NFR-7). FR-C2 keeps accepting 5.x *connections* either way
  - **T4** — a Ghost(Pro) **Starter** site (verifies the Preview-only path)

  **Deployable targets are T1–T3.** Wherever an exit criterion says "all Ghost deploy targets (§4)", it means: deploys succeed end-to-end on T1–T3. **T4's criterion is narrower and specific:** a deploy attempt against T4 fails with the friendly Starter message and sets Preview-only. FR-C2's `hostSettings.limits` probe sets the same flag at connect and clears it when the probe changes, so both the setting and the clearing path are testable on T4 itself; the deploy error remains authoritative.

  This is safe because the product has no users pre-launch. User-journey E2E tests exercise the production stack end-to-end as a real user. Of the four NFR-6 gates, **only two touch a real Ghost**: the nightly perceptual diff (NFR-6(c3)) and the E2E suite (NFR-6(d)) — both serialized per target, because theme activation is globally stateful, so concurrent runs queue and never interleave. The render matrix (NFR-6(a)) renders locally and needs no Ghost; compile CI (NFR-6(b)) needs only gscan; NFR-6(c1)/(c2) run per-commit against committed snapshots and recorded output. Budget the CI lane accordingly.

  **The §4 test targets are exempt from FR-J11's 10/hour per-site deploy rate limit.** A single DoD run is 30 serialized starter deploys, which the limit alone would stretch past three hours before compile time, and every re-run would pay it again.
- **Definition of Done for GA:** every FR implemented; every section variant passes the render matrix (NFR-6(a)) **and** the NFR-5 accessibility scan; 10 starter templates deployable end-to-end to all Ghost deploy targets (§4); marketing site live with full sections gallery; billing verified with real Dodo test-mode → live-mode transactions; rollback verified; **docs complete** — every page enumerated in FR-N4 exists, is non-empty, and carries the "Suggest an edit" affordance.
- **No de-scope contingency (owner decision):** the full FR scope and the 485-variant inventory are not de-scopeable; if library waves slip, launch slips. The sections are the heart of the tool — every one must work perfectly (the NFR-6 gates enforce this).
- **Post-launch topology (Test vs Live):** at go-live, a fresh infrastructure set is provisioned as **Live** (new Supabase project, Vercel production environment, live Dodo) and takes over the production domains; the existing pre-launch stack — including Ghost targets T1–T4 — becomes the permanent **Test** environment on test domains. From the first customer onward, all testing (E2E, render matrix, the NFR-6(c) fidelity layers) runs exclusively against Test; real-user data exists only in Live. Test is a permanent, costed line item, not a pre-launch expense that ends at GA (Appendix F).
- **Cutover migration.** Three record sets are exported from Test and imported into Live at cutover: **suggestions**, their **votes** (FR-M2), and the **dogfood project** that builds Inflozo's own Ghost theme (FR-N5). Everything else starts empty in Live. Without this the public suggestions board — which has been collecting real submissions from real visitors on the real marketing site — resets to zero on launch day.

## 5. Functional Requirements

Requirements are numbered `FR-<domain><n>`. "Must" is the default force. Free/Pro gating is defined in Appendix F. Sections are ordered by dependency, not alphabetically — FR-Q (Theme Settings) sits between FR-I and FR-J because routing and theme settings both feed the compiler.

### FR-A · Authentication & Accounts

- **FR-A1** Sign-up and sign-in via **magic link** (Supabase Auth email OTP link) with branded email template. No passwords exist anywhere in the product.
- **FR-A2** **Passkey** support via Supabase Auth's native passkey (WebAuthn) capability. Because Supabase requires a signed-in session to register a passkey and the API is in Beta (as of May 2026; requires `@supabase/supabase-js` ≥ 2.105.0 with explicit opt-in), the flow is: magic link first → post-onboarding nudge + Account → Security page to register a passkey → subsequent sign-ins offer passkey as the primary, magic link as fallback. Feature-flag the passkey module so it can be disabled without redeploy if the experimental API changes.
- **FR-A3** Account → Security lists registered passkeys (auto-named from authenticator AAGUID) with rename and revoke.
- **FR-A4** Email change with re-verification of the new address; a change to an address already registered to another account is rejected upfront ("already in use") before any verification email is sent.
- **FR-A5** Account deletion: cascades projects, templates, assets, connections, and deploy artifacts; suggestions-board posts are anonymized (author becomes "Deleted user", any uploaded image is removed) and the user's votes and notification rows are deleted; honors a 14-day soft-delete window then hard purge (GDPR). Signing in during the soft-delete window offers a one-click "Restore account" that cancels the purge. **Subscription state across the window is explicit:** soft-delete stops the Dodo subscription's auto-renew immediately, so a deleting user is never charged again while the purge is pending, and entitlements are retained at their current level until the purge; restoring within the window offers one-click resume of auto-renew at the same plan and price, and says plainly when the paid period ended meanwhile — that account restores on Free, under FR-L3's over-limit rules. **Pre-Inflozo snapshots are offered as a download before the purge:** every retained snapshot (FR-J13) is listed with its site and the purge proceeds only once the user has downloaded or explicitly declined them, because the user's live site may still be running an Inflozo theme.
- **FR-A6** Sessions persist 30 days rolling; a sign-out-everywhere action is available.

### FR-B · Projects & Dashboard

- **FR-B1** Dashboard shows projects as cards: auto-captured canvas thumbnail, project name, linked-site badge (favicon + name) or "Sample content" badge, last-deploy status chip (Live vX / Never deployed / Failed), updated-at. **The thumbnail is captured client-side from the same-origin canvas** (§7.3) and uploaded to the `thumbnails` bucket — no headless browser and no server-side render of the section runtime exists anywhere in the product.
- **FR-B2** Create project from: **Starter template** (Appendix E, with full-page scrollable preview in light and dark before choosing), **Blank canvas**, **Duplicate** of an existing project, or **Redesign proposals** (FR-C7, for connected sites). Style Pack chosen at creation (changeable anytime).
- **FR-B3** Rename, duplicate, delete (type-name-to-confirm) on every project. Deleting a project whose theme is live on a connected site warns that the site's active theme and its rollback history came from this project; the project's deploy artifacts are purged with it, while the per-site pre-Inflozo snapshot survives (FR-J13). Renaming after first deploy changes the display name only (FR-J10).
- **FR-B4** Plan caps enforced at creation time with a contextual upgrade prompt (Free: 1 project; Pro: 25).
- **FR-B5** A project targets at most one connected site at a time (switchable). Unlinked projects render the bundled sample dataset (FR-H3).
- **FR-B6** Dashboard also surfaces: a connected sites strip with health badges, an asset quota meter, and a "What's new" changelog popover.
- **FR-B7** **Notifications center:** a bell in the dashboard and editor top bars opens a per-user notification feed — deploy outcomes, site health changes (reconnect needed), **Ghost-compatibility notices (FR-C5)**, billing events (payment failed / grace), library "updates available" notices (FR-J14), and product announcements. Unread badge, mark-all-read, 90-day retention — **site-health and compatibility notices are exempt from the prune** and are retained until read or resolved, because the population they are written for is precisely the population that deployed once and stopped signing in. In-app only except where FR-P1 names an email for the same event; email policy remains FR-P.

### FR-C · Ghost Site Connections

- **FR-C1** Connect flow: user enters their Ghost URL → guided, screenshotted instructions to create a **Custom Integration** in Ghost Admin **and to mint a Staff Access Token on the site Owner's account** → user pastes the **Admin API key**, the **Content API key** and the **Staff Access Token** → Inflozo validates all three. The Staff Access Token is required, not optional: Ghost's integration-token allowlist blocks every `GET /themes/*` call, so without it there is no pre-Inflozo snapshot (FR-J13) and no pre-deploy drift check (FR-J16), and the connect flow says so in those terms.
- **FR-C2** Validation (server-side): mint the short-lived Admin JWT and call the **authenticated** `GET /admin/config/` endpoint. `GET /admin/site/` must **not** be used to validate a key — it is mounted on Ghost's public admin router, whose middleware chain contains no authentication step, so it returns 200 for a fabricated, malformed or revoked key and validates nothing. `/config/` proves the credential, reports the Ghost `version` (5.x and 6.x accepted; 4.x and older rejected with a "please update Ghost" message), and carries `hostSettings`. The Content API key is verified client-side with a `settings` read. **Plan awareness is probed, not asked:** on a Ghost(Pro) site `hostSettings.limits.customThemes` reports whether custom theme upload is permitted — its absence (self-hosted) means unlimited — so the connect flow marks a site **Preview-only** automatically where the limit forbids custom themes (**Ghost(Pro) Starter**, in Ghost's 2026 Starter/Publisher/Business lineup), and clears the flag automatically when a later probe (FR-C5's daily check) reports otherwise. The shape is undocumented and host-controlled, so the probe carries a fallback: where `hostSettings` is present but unreadable, the flow asks the user which plan the site is on. **The deploy error remains authoritative:** a rejected theme upload fails with a friendly explanation, a "check or upgrade your Ghost(Pro) plan (Publisher or higher)" prompt and a docs link, and sets Preview-only; a successful deploy clears it. There is no user-declared-plan step in the happy path and no plan field in Manage keys (FR-C8). Live-content editing requires the site to be reachable over HTTPS from the browser (Content API fetches are client-side): `http://` URLs are warned at connect, and when client-side Content API reads persistently fail for a validated connection (CORS proxy, mixed content), the editor names the cause and falls back to sample content rather than failing silently. **Code-injection notice:** connect computes one boolean — whether the site's settings carry head or foot code injection — and, when true, surfaces a one-time notice that the live page can legitimately differ from the canvas in ways Inflozo does not control (§1.2). Only the flag is computed, server-side and discarded; the injected content is never returned to a client, never stored and never enters a render path, so NFR-3's never-read rule over the canvas stands.
- **FR-C3** Key security: Admin API keys and the Owner Staff Access Token are encrypted at rest with Supabase Vault and **never sent to any client**; all Admin API calls are proxied through server routes that mint the required short-lived JWT per request. The Content API key is browser-safe by Ghost's design and is delivered to the editor for direct client-side content fetches.
- **FR-C4** **Auto-branding:** on successful connect, fetch site settings (title, description, logo, icon, cover image, accent color, navigation) and present a one-click "Use your brand" card that seeds the active project's Style Pack accent + logo + nav and switches the canvas to live content. Skippable; re-runnable later from the Style panel.
- **FR-C5** Multi-site: Free 1 connection, Pro 10. A daily background health check re-validates the stored credentials against `GET /admin/config/`, re-runs version detection (so a Ghost version upgrade lifts stale version-dependent behavior without reconnecting), re-runs FR-C2's `hostSettings.limits.customThemes` probe (so Preview-only sets and clears without any user action), and **re-reads the live `routes.yaml`** to detect routes drift against what Inflozo last offered (FR-I4); failures set a "Reconnect needed" badge. The email notice sends once per healthy→unhealthy transition (at most one reminder), is suppressed while the outage persists, and resets on recovery — subsequent failures log to the notifications center (FR-B7) only. Regardless of transitions, at most **one health email per site per rolling 7 days** (a flapping site logs to the notifications center, never to email). **Compatibility watch — one broadcast per Ghost release, all plans:** on each Ghost release Inflozo re-verifies the shipped library against it using each variant's `ghostCompat` (FR-G3) and posts a single notice to every account — normally a confirmation that the library was verified, and where the release does affect shipped variants, a notice naming the affected categories and recommending a redeploy through FR-J14. There is no per-site analysis and no per-release compatibility data to author, and the watch is not Pro-gated because the risk is not plan-dependent. The affecting variant of that notice is the one compatibility carve-out FR-P2 allows to reach email (FR-P1). **A compatibility redeploy is a first-class exempt path:** it re-ships a design that already ran, so — exactly like rollback (FR-J9) — it does not require the edit lock (FR-D18), is not gated behind FR-J14's mandatory library-update confirm, and is not blocked by FR-L3's Pro-section exit rule on a lapsed account. A redeploy that would also carry unshipped editor changes is an ordinary deploy and is gated normally.
- **FR-C6** Disconnecting a site never deletes projects; affected projects fall back to sample content. Disconnecting also never deletes the site's pre-Inflozo snapshot: **snapshots are bound to the site record id, not the raw URL** (FR-J13), so a disconnected site's record and its snapshot are retained and re-adopted when that same record is reconnected. Reconnecting a URL for which no record is retained creates a **new** site record with no snapshot association — Inflozo never adopts a snapshot on a URL match alone, because the same URL can serve a different Ghost install after a staging cutover or a rebuild; the new record captures its own snapshot at Inflozo's first upload to it. A snapshot whose site record has been disconnected for **90 days** is an orphan and is purged, after a notice and a download offer (the FR-A5 rule applies).
- **FR-C7** **Redesign proposals:** after connect + auto-branding, offer a one-click "redesign my site" pass that renders 2–3 starter + Style Pack combinations populated with the user's real content; picking one creates the project pre-assembled. Variety is an acceptance criterion: proposals must differ in layout structure, not merely palette. Re-runnable: the same flow is available anytime from the dashboard's "New project" path for any connected site, not just during onboarding.
- **FR-C8** **Key rotation & reconnect:** per-site "Manage keys" flow — re-paste the Custom Integration's Admin and Content keys and the Owner's Staff Access Token, test the connection, save re-encrypts to Vault (FR-C3). Surfaced from the site card and from every "Reconnect needed" state. **A site's URL is immutable — there is no edit-URL-in-place.** A domain move is a **disconnect + reconnect**: the user connects the new URL as a new site, pastes that site's own keys, and Inflozo re-reads its content (posts, pages, tags, authors, tiers, settings) against the new record; projects are re-pointed with FR-B5's site switcher and the old record follows FR-C6's orphan rule. Editing a URL in place would carry one site's record, snapshot and first-upload flag onto a different live Ghost install — so "restore the original theme" could push one site's archived theme over another's, and the new site would never be snapshotted at all — which is why the affordance does not exist rather than being guarded. There is no plan field in this flow: Preview-only is probed, not declared (FR-C2). A new-site connect whose credentials match an existing record still hints "Moved domains? Reconnect the new URL and re-point your projects — your old site's snapshot is kept for 90 days."

### FR-D · Editor Core

- **FR-D1** Layout: slim top bar; collapsible left **Layers** panel; center **canvas**; right **Controls** sidebar. With nothing hovered/selected the canvas is a pixel-faithful render of the site (P1). Panels may remain visible; the canvas itself carries zero editing chrome.
- **FR-D2** Hover state on a section: 1px outline, floating name tag, and quick actions — Variant Shuffle ◀ ▶, Duplicate, Delete, drag handle. Between sections, a hairline "+" insertion affordance appears on hover.
- **FR-D3** Click selects a section (persistent outline + sidebar controls). Esc deselects. Clicking a text element inside a selected section enters inline editing.
- **FR-D4** **Inline editing:** every text prop is editable directly on canvas (line breaks honored; per-prop character limits from the section schema). Selecting text raises a small floating toolbar (Koenig/Medium-style) offering exactly four inline marks — **bold, italic, underline, link** (link via the Link Picker) — available on any text prop, headlines included (exception: a prop bound to a Ghost Admin text setting is plain-text-locked while bound — FR-Q3). **Rich-text model:** a text prop's value is stored as **text plus marks in a JSON structure** — a plain string with an ordered list of `{start, end, mark, href?}` ranges over exactly those four marks — never as an HTML string. Canvas editing is raw `contenteditable` mapped to schema props by data-attributes (§7.3), so no editor library's DOM enters the iframe and the rendered markup stays byte-comparable to shipped markup; the sidebar's Content field edits the same structure, which is why both editors can show marks. The compiler is the single serialization point: it escapes the text and emits the mark ranges as `<strong>/<em>/<u>/<a>`, so unescaped user HTML can never reach the theme (FR-J1's inert-emission rule), and FR-Q3's plain-text lock is a truncation of the mark list rather than a parse. Compiled output is clean `<strong>/<em>/<u>/<a>`; pasted content is stripped to these marks. Every text prop is *also* editable in the Content group of the sidebar (owner requirement). Clicking an image opens the asset picker popover.
- **FR-D5** **Layers panel:** ordered section list for the active template; drag to reorder with live canvas follow; per-instance rename; duplicate/delete; visibility toggle (hidden sections are excluded from compilation but retained). Site-wide sections (headers, announcement bars, footers) are single shared instances: they appear in every template's Layers panel as a pinned "Site-wide" group with a globe badge, and editing them changes every template (they compile into `default.hbs`). Site-wide singletons cannot be duplicated; deleting or hiding one asks a confirm noting it affects every template (hiding the footer still triggers FR-J15's Free credit fallback). **Non-placeable treatments never appear in Layers:** the 28 variants of A32 (Paywall / Content CTA), A33 (Koenig card treatments) and A34 (pagination styles) are chosen elsewhere — the Paywall editor (FR-H6), the Post Content Layout's Style group, and the designated main feed's Pagination control (FR-H2) — apply once per project, and are excluded from placement, drag, reorder, duplicate and delete (`sections-inventory.md` § Placeable sections vs non-placeable treatments). **CTA-bearing sections carry a member-visibility control** — show to Everyone / Logged out / Free members / Paid members — evaluated against `@member` on the live site and previewed via FR-D16; this is how a member ask is placed on a canvas now that the paywall is a template surface rather than a section. **Hiding every section is not emptying:** a fully hidden template is designed and compiles an empty body; only removing every section returns a template to untouched (FR-I1).
- **FR-D6** **Template switcher** in the top bar: Home, Post, Page, Tag archive, Author archive, **Membership (Signup / Signin / Member Home)**, 404, a conditional **Private** canvas, plus any custom templates created in the Routes Manager (FR-I). **The membership canvases are custom page templates, not a members template family:** Ghost 6 has no `members/*.hbs` family and never rendered one (`research-ghost-membership-pages.md` §1, §9), so each compiles to `custom-{name}.hbs` at the theme root and is bound to an ordinary Ghost Page by the user picking it from the **Template** dropdown in Ghost's page editor — no `routes.yaml`, no Routes Manager visit, and no Ghost Admin step beyond that one choice (FR-I1, FR-I5). The Private canvas follows the same conditional pattern: it appears once a Private Site Gate (Appendix A §31) is called for, opens empty, and compiles `private.hbs` only when designed (FR-I1) — without it that variant is a launch deliverable with no surface that can create it. **Synthesis applies to exactly six templates** — `index.hbs`, `post.hbs`, `page.hbs`, `tag.hbs`, `author.hbs`, `error.hbs`: untouched, these compile from the normative **Synthesis Defaults** (`sections-inventory.md` § Synthesis Defaults — per-template default section stacks, all [Free] variants, with inheritance rules), so a home-only design still produces a complete, coherent theme: header/footer/style are inherited from the Home canvas by reference, body stacks come from the defaults tables, and archive defaults ship a designated main feed (FR-H2). Every other canvas — the membership pages, Private, and every custom template — is **never synthesized**: it opens empty and emits nothing until designed. Opening one of the six untouched templates renders its default stack as the starting canvas; the first edit materializes that stack into the project doc.
- **FR-D7** **Light/Dark authoring:** sun/moon toggle re-renders the canvas in the other mode. Mode-scoped controls (Background role, per-mode image swaps, mode-specific toggles) apply to the active mode only and display a moon badge when a dark override exists; "Clear dark overrides" per section. Project setting: **Light only** or **Light + Dark** (default: **Light + Dark** — every preset ships a hand-paired dark palette, so dark is prepaid). Light-only projects hide the toggle and compile without dark support. Switching a Light + Dark project to Light only keeps existing dark overrides inert — nothing is deleted; they reapply if dark is re-enabled. Switching between Light only and Light + Dark never affects the custom-settings cap — the built-in slots are reserved unconditionally (FR-Q2).
- **FR-D8** **Device preview:** Desktop / Tablet (834) / Mobile (390) view toggles — display only, and unrelated to a **Preview-only** connection (Appendix I). Sections are auto-responsive; there is no per-breakpoint editing.
- **FR-D9** Undo/redo: 100-step history covering content, controls, ordering, shuffles, and Style Pack changes. The undo stack persists locally (per browser) across reloads and sessions — a deleted section is recoverable with all its customizations via undo even after a reload (persistence model in FR-D10; durability is bounded by the browser — the app requests persistent storage via `navigator.storage.persist()`, but an evicting browser can still clear it, so the promise is scoped to "while browser storage survives"). Undo entries whose section schema no longer matches the current library no-op gracefully with a notice (never corrupt state). On a hydrate that **supersedes** the local document — a takeover (FR-D18), or any lock acquisition where the cloud snapshot's revision differs from the local doc's base revision — the local undo journal is **cleared**: its entries reference a superseded document and must never replay (AD1). An ordinary reload that re-acquires the lock against a matching revision keeps its journal, which is what makes undo-after-reload real rather than nominal. The testable claim is scoped to match: **the journal is present and replayable after a reload within the same session**; loss to browser eviction is a stated limitation, not a requirement.
- **FR-D10** **Local-first persistence:** every change is written immediately to local browser storage — writes never block the UI, and editing speed is unaffected (NFR-1). Cloud sync to Supabase runs periodically (default: every 3 minutes), on tab close, on lock release (FR-D18), and before any deploy or export. Manual save (⌘S) is always available. The periodic cloud autosave can be toggled per user; local persistence is always on. Indicator states: Saved locally / Syncing / Synced / Retrying (offline retry queue). If local storage is unavailable or a write fails (quota, private mode), the editor falls back to immediate per-change cloud sync and says so in the indicator — never a false "Saved locally". (Fallback mode is a degraded state exempt from NFR-1's no-added-latency clause; the indicator makes the mode visible. AD3's rejection of per-change sync applies to the default path only.) Turning the periodic cloud autosave off shows an explicit data-loss warning (browser storage can be evicted). On lock acquisition (FR-D18) the cloud snapshot is authoritative **whenever its revision differs from the local doc's base revision**: the local doc is replaced before editing resumes, so a stale local copy never overwrites synced work — while a matching revision (the ordinary reload) hydrates in place and keeps the undo journal (FR-D9). (Mechanism: `addendum.md` §AD1.)
- **FR-D11** Keyboard: ⌘K insert section · [ and ] shuffle variant · ⌘D duplicate · Del delete · ⌘Z / ⇧⌘Z · ⌘S save now · 1/2/3 device preview · L layers · . (period) dark toggle · Esc deselect.
- **FR-D12** **Section Picker:** full-screen overlay with left category rail, search, and live previews rendered *in the project's current Style Pack* with the project's content source — the user browses the library already wearing their brand. Free/Pro badges; Free users can add any Pro section — the canvas is open; enforcement happens at the exits (FR-L3). Insertion lands at the invoked position. **The Picker filters on context:** it offers only variants whose `bindingContext` and `compileTarget` (FR-G3) match the template being edited, so a section binding a resource the template does not have — or compiling into a different file — is never presented (FR-H7's prevention rule, applied to placement). The 28 non-placeable treatments (A32/A33/A34) are absent from the rail entirely.
- **FR-D13** **Variant Shuffle:** cycles the selected section through its category's variants in place — **restricted to variants sharing the placed instance's `bindingContext` and `compileTarget`** (FR-G3), so a shuffle never lands on a variant that binds a resource the current template lacks or that compiles into a different file. Where a category's variants differ on those values (A29 tag vs author, A31 error vs private vs custom page) the ring is **partitioned** and the arrows cycle only the matching partition. **A30 is partitioned on a different axis:** its three membership surfaces — signup · signin · member home — share one `bindingContext` and one `compileTarget` (`custom-{name}.hbs`, FR-I1), so FR-G3's mechanical partition does not separate them; A30 therefore declares an explicit **surface** partition that Shuffle and Site Remix never cross, because those surfaces differ in form markup and content model rather than in render context. The shared per-category content model remaps the user's content; props a variant doesn't use are preserved invisibly and restored if shuffled back. The same rule governs list items: a variant renders only as many items as its structure fits (8 items shuffled into a 3-card layout shows 3); surplus items are preserved invisibly and reappear on shuffling back, and the sidebar shows the count ("8 items · 3 shown in this design"). Works via hover arrows, sidebar carousel, and [ ] keys.
- **FR-D14** Canvas is site-width, fit-to-viewport with vertical scroll. No zoom in v1. No hard cap on sections per template (a deliberate contrast to competitors' structural caps); the editor must hold NFR-1 performance on the 40-section stress fixture (NFR-1); beyond it, behavior degrades gracefully — slower is acceptable, lockups and state corruption are not. **"Lockup" is bounded as any main-thread block over 5 seconds**, so the clause has a pass/fail condition on the stress fixture.
- **FR-D15** Content-source pill: "Previewing with: {site} / Sample content", switchable when a site is linked.
- **FR-D16** **Member-state preview:** view canvas as Anonymous / Free member / Paid member — Appendix B's fourth `@member` status, `comped`, **previews as Paid**, differing in billing rather than access; members-aware sections (nav auth links, subscribe CTAs, paywall) re-render accordingly. With a linked site, gated post bodies render Orbit Weekly stand-in text with a "gated content — shown with sample text" indicator: the browser-safe Content API never returns members-only content, so real gated bodies are not previewable (the NFR-6(c) fidelity layers exclude gated-body equivalence).
- **FR-D17** **Site Remix:** one action re-rolls the whole canvas — Style Pack and/or every placed section's variant — with all content preserved via the shared per-category content model (FR-D13). **Every re-roll obeys FR-D13's context restriction:** a section is only ever replaced by a variant sharing its `bindingContext` and `compileTarget`, on every template Remix touches, so a one-click re-roll can never move a section onto a resource its template does not have or into a different compiled file. Scoped re-roll (pack only / variants only), single-step undo, and never-lose-content are hard requirements, gated mechanically as **zero prop loss across N shuffles and a full re-roll on the 40-section stress fixture**. Site-wide singletons (header/announcement/footer) are excluded from Remix unless explicitly included, and the non-placeable treatments (A32/A33/A34) are never re-rolled.
- **FR-D18** **Edit lock (single active editor):** one editing context per project across tabs, browsers, and devices. Opening the project elsewhere yields read-only mode with a "Request editing" nudge. On accept, the current holder syncs its changes to the cloud, releases the lock, and becomes read-only; the requester gains edit rights. Locks carry a heartbeat whose payload includes the holder's **unsynced-edit count** — user-perceived edits, never raw operations; `addendum.md` §AD2 states the ops→edits mapping (a shuffle is one edit however many ops it costs), because this number appears verbatim in the string that tells a user what they lost. If a nudge goes unanswered, the requester is notified — "No response; that session has X unsaved edits" — and may take over anyway: the lock transfers, the requester refreshes to the last synced snapshot, and starts editing. A revived former holder becomes read-only and is told concretely what was lost — the message states the count in edits ("That session had 14 unsaved edits; they were not included"); those edits are not recoverable (the device's local journal is cleared on its next hydrate — FR-D9/AD1). **Deploy and ZIP export require the edit lock:** from a read-only session, invoking Ship it or Export first prompts a take-over — surfacing "X unsaved edits exist elsewhere" — so a stale cloud snapshot can never silently ship. (Mechanism: `addendum.md` §AD2.)

### FR-E · Style Packs

- **FR-E1** Token set per pack: colors ×2 modes (background, surface, text, muted text, border, accent, on-accent), heading font + body font (from a curated pool of **30 Google Fonts pairings, enumerated in Appendix D** — self-hosted in generated themes at compile, FR-J3; each pairing declares its two families, the weights shipped, and whether it ships as a variable or a static face, because all three determine `@font-face` emission and bundle size), radius scale (Sharp/Soft/Round), spacing density (Compact/Comfortable/Airy — a pack-level token, distinct from the per-section Vertical spacing scale Compact/Comfortable/Spacious), **site width (Narrow/Normal/Wide) + gutters (Tight/Normal/Loose — its own scale, deliberately not the per-section Vertical spacing labels)** (sections span the site width by default and stay responsive within it), button style (Solid/Soft/Outline/Pill), shadow level (None/Subtle/Lifted), link style (Underline/Accent).
- **FR-E2** **12 curated presets** ship, each with hand-tuned paired light + dark palettes (Appendix D). Switching packs restyles the entire canvas live — this is a designed "wow" moment (≤ 300 ms crossfade).
- **FR-E3** Every token is user-editable per project (color pickers and font pairing list live here and only here — P2). Per-mode palette editing. Custom packs are deliberately per-project — there is no account-level custom pack library in v1 (duplicate a project to carry a look forward). Token edits run a live AA contrast check on token pairings and warn on failures (mirroring FR-Q5's promotion caution) — a warning, never a block.
- **FR-E4** Tokens compile to CSS custom properties in the generated theme: light values on `:root`, dark values in a `prefers-color-scheme: dark` media query (applied when `color_scheme` is Auto — pure CSS, so Auto works with JS disabled) and on `[data-mode="dark"]`, which the mode-toggle JS sets to override the system preference when the visitor picks a mode explicitly. Sections consume tokens exclusively, so pack changes can never break a layout.
- **FR-E5** Auto-branding (FR-C4) seeds accent color and logo into the active pack.

### FR-F · Control System (the disciplined vocabulary)

- **FR-F1** Controls come from a **shared vocabulary of simple, visual, named-value types**. Core set: **Layout Picker** (mini-diagram thumbnails), **Segmented Control**, **Stepper** (e.g. columns 2/3/4), **Toggle**, **Named Select** (word values only), **Swatch Row** (Style Pack roles: Base/Surface/Accent/Contrast/Image — never a color picker), **Image Picker** (opens Asset Library), **Icon Picker** (curated Lucide set), **Link Picker**, **Text Field/Area**, **Date Picker** (calendar popover, site timezone — e.g. countdown targets). The vocabulary may grow when a section genuinely needs a new type, provided the control stays simple and P2-compliant (visual/named values — never raw CSS, units, or hex). One shared type per need; no per-section one-offs.
- **FR-F2** No units, no hex, no CSS concepts at section level (P2). Spacing = Compact/Comfortable/Spacious. Site width and gutters are Style Pack tokens (FR-E1); sections span the site width by default — width is not a per-section control.
- **FR-F3** Sidebar structure: 3–5 **Quick Controls** pinned on top (chosen per section as the highest-impact decisions), then Content / Layout / Style / Data accordion groups. Hard cap ≈ 15 visible controls per section; Data group appears only on dynamic sections. **Three universal controls sit on every section** — **Background role** (Swatch Row), **Vertical spacing** (Compact/Comfortable/Spacious) and **Top divider** (None/Line/Fade). They are declared once in `sections-inventory.md`, not per category, are **exempt from the ≈ 15 cap** (which governs a category's own controls, so the effective ceiling is ≈ 15 + 3), and are never Quick Controls.
- **FR-F4** Per-control reset-to-default and whole-section reset. Every control change paints its optimistic UI within one frame; the resulting canvas re-render completes within G6's 100 ms budget on the NFR-1 reference environment (one budget per interaction — no competing numbers).
- **FR-F5** Mode-scoped controls carry a moon badge when a dark override exists (FR-D7).
- **FR-F6** **Link Picker** is Ghost-aware: internal pages/posts/tags/authors (live-searched from the connected site, or sample data), **Portal actions** (Sign up, Sign in, Account, Upgrade — compiled to the `data-portal` values Appendix B enumerates; the Upgrade action emits **`account/plans`**, never `upgrade`, which Portal does not parse), external URL, and email. Internal link targets are re-validated against the connected site at compile; dead links (target deleted on Ghost) and links minted against a different site surface as pre-deploy warnings.
- **FR-F7** Controls are schema-driven from the section registry: one schema definition powers the sidebar UI, validation, defaults, dark-override capability flags, and the compiler (P4).

### FR-G · Section Library

- **FR-G1** The library ships with **34 categories and 485 unique variants at GA** as inventoried in Appendix A — 485 is a floor, not a fixed total, since the library grows post-launch per FR-J14. Appendix A is normative: every listed variant is a launch deliverable. **457 are placeable sections and 28 are non-placeable treatments** (A32 paywall designs, A33 Koenig card treatments, A34 pagination styles), chosen outside the canvas; every requirement quantifying over "every variant" — FR-G5's uniqueness bar, FR-G6 and NFR-6(a)'s render matrix, NFR-5's accessibility scan, the FR-N2 gallery — still covers all 28, in the host contexts `sections-inventory.md` names for them.
- **FR-G2** Every category ships **at least 2 Free-tier variants**, and where a category's variants split across `compileTarget`s or `bindingContext`s (FR-G3) **the Free options are distributed across those contexts**, not clustered in one — a Free user who opens a canvas must find something they can put on it. **70 variants are [Free]:** the first two of every category (68), plus **A29 #7** and **A31 #10**, re-tiered so the author-archive binding context and the `private.hbs` compile target each carry a Free option of their own. **A30 needs no re-tier of its own:** all 13 of its variants share one `bindingContext` and one `compileTarget` (FR-I1), and its first two — **#1 Signup Center Card** and **#2 Signin Minimal** — are already [Free] and cover the two membership surfaces a Free user actually lands on. The floor is guaranteed for every context reachable from the six synthesizable templates (FR-D6) and for `private.hbs`. It is **not** guaranteed for contexts a user reaches only by opting into an optional surface — custom page templates created in the Routes Manager (A31 #6/#7/#9) and A30's **member-home** surface — where a Free user may find only Pro options; FR-L3's block sheet must therefore offer "remove the section" alongside "swap to a Free variant", because there is not always something to swap to. Free variants are marked [Free] in Appendix A; all others are Pro.
- **FR-G3** Section registry entry format: `{ id, category, name, tier, bindingContext, compileTarget, contentSchema, controlSchema, quickControls[], html, css, js?, dataBindings?, ghostCompat, darkCapabilities, previewSeed }`. **`bindingContext`** names the Ghost resource a variant binds (`none` · `post` · `posts` · `tag` · `tags` · `author` · `authors` · `tiers` · `error` · `private`; `@site` and `@member` are universal and never narrow it) and **`compileTarget`** the file it compiles into; both are declared per category, or per variant where a category's variants differ, and together they are the filter FR-D12, FR-D13 and FR-D17 obey and the placement half of FR-H7's context rules. **`ghostCompat: { minVersion, helpers[], deprecatedAt? }`** records the helper surface and version floor each variant depends on; it is authored *with the variant*, never per Ghost release, which is what makes FR-C5's per-release verification a mechanical check rather than a standing editorial job. **`quickControls[]` is a convention, not a second authoring pass:** the first 3–5 entries of a category's `Controls:` line in `sections-inventory.md` *are* its Quick Controls, in order (FR-F3), so the array is recovered mechanically and the two documents cannot drift. Section source is **annotated HTML, not Handlebars** (§7.3, P4) — the same file the canvas renders and the compiler serializes — and its authoring format and directive vocabulary are a **documented deliverable**, since all 485 sections are authored by the dev team against it. `css` is **plain CSS consuming Style Pack custom properties only**, authored outside the app's build pipeline and explicitly excluded from any Tailwind processing the Next.js app adopts; utility classes are structurally incompatible with FR-E4's token-only styling. `{{#get}}`-bearing variants may reference **only template-level context** in their filters, never the current render context (FR-H5) — a registry-level constraint on what the library may express, binding on every variant authored under E9–E11. The registry is data + files, versioned in the repo, and is the single input to both the editor runtime and the theme compiler. **Every deploy records the variant manifest it shipped** — variant ids plus the library version — on its deploy row, so FR-J14's confirm step and FR-J9's history can name what is actually live without unzipping an artifact.
- **FR-G4** Every variant must be: responsive 390 → 1440+ with no horizontal overflow; WCAG 2.1 AA (contrast via token pairs, focus-visible, semantic landmarks — the AA guarantee is scoped to shipped packs and library defaults; user token edits are warned, never blocked, FR-E3); token-driven only; functional with JS disabled (JS is progressive enhancement — marquees pause, accordions render open, load-more **and infinite scroll** fall back to numbered links, and Auto dark mode applies via the `prefers-color-scheme` media query — FR-E4).
- **FR-G5** Uniqueness bar: variants within a category must differ in **layout/structure**, not merely spacing or emphasis. The bar carries a **mechanical proxy** so it is not tested by unaided human judgment across ~3,500 pairwise comparisons: every variant declares the structural descriptor that follows its name in Appendix A, and **no two variants in a category may share a structural descriptor tuple** — a CI assertion over the inventory. A reviewer must still be able to name what is structurally different about any two variants; the proxy makes the failure case findable, not the judgment unnecessary.
- **FR-G6** Section CI (see NFR-6): every variant renders in the matrix (3 Style Packs × light/dark × 3 viewports), compiles into a sample theme that passes gscan, and has a stored screenshot baseline for visual regression.

### FR-H · Data Binding & Content

- **FR-H1** The Ghost data surface available for binding is cataloged in Appendix B. It reflects the Ghost Content API resources — **Posts, Pages, Tags, Authors, Tiers, Settings** — plus Handlebars template context (`@site`, `@member`, pagination) available at render time on the live site.
- **FR-H2** Dynamic sections expose a **Data** control group: Source (Latest / Featured / By tag / By author / Hand-picked posts), Count, Order (Newest/Oldest), and show/hide toggles for meta (date, author, excerpt, reading time, tag chip). On every template Ghost natively paginates — **index, custom collections, channels, and the tag and author archive templates** (Ghost serves archives and channels the same paginated `posts` context and `/page/N/` URLs as collections; a `{{#get}}`-driven feed with a fixed Count renders identical content on every page of an archive) — exactly **one section is designated the main feed**: it is bound to the native paginated `posts` context (never `{{#get}}`), sized by the global `posts_per_page` (FR-Q1) instead of a Count, and it alone exposes **Pagination style: Numbered (`/page/2/`) / Load More / Infinite scroll** (designs in Appendix A §34). All other feed sections are `{{#get}}`-driven: fixed Count, never paginated. The editor marks the main feed visibly. A paginated template with **zero** feed sections is allowed (e.g. a feed-less marketing homepage): pre-deploy checks warn that the template's `/page/N/` URLs would duplicate the page, and the compiler emits an SEO guard on such templates (`noindex` beyond page 1 plus a canonical link to page 1) so Ghost's automatic pagination never produces indexable duplicates. Designation has a defined lifecycle: the first feed section placed on a paginated template auto-designates as the main feed (tag and author templates start with a designated main feed from the Synthesis Defaults, and a channel template created in the Routes Manager is given one the same way at creation); deleting or hiding it transfers designation to the next feed section (or the zero-feed rules apply); the user can reassign it anytime.
- **FR-H3** **Sample dataset "Orbit Weekly":** a bundled fictional publication — 12 posts with feature images/excerpts/reading times, 6 tags, 3 authors with portraits and bios, 2 tiers (Free + "Supporter" with monthly/yearly prices and benefits), nav, and brand assets. All imagery is internally produced (license-clean). Every section's `previewSeed` maps into this dataset so any section drops in looking finished.
- **FR-H4** With a linked site, the editor fetches real content **client-side** from the site's Content API (browser-safe, cacheable by design) with SWR-style caching (60 s) and silent fallback to Orbit Weekly on network failure (with a subtle indicator). **Reads are batched and de-duplicated per resource** across the canvas, Section Picker previews and Link Picker search, under a per-session request ceiling; on HTTP 429 or repeated failure the editor falls back to Orbit Weekly and **names the cause**, because Ghost rate-limits Content API keys and Ghost(Pro) sits behind an edge Inflozo does not model. The canvas reads list and metadata fields only and **never post or page body HTML** (NFR-3): `{{content}}` renders dummy placeholder prose in every content layout. When the site has fewer or zero items than a section requests, the canvas renders what exists plus an editor-only indicator ("this site has 2 posts; section shows up to 6"); compiled sections render gracefully with fewer items, and a section bound to zero items renders nothing on the live site.
- **FR-H5** **Canvas rendering & helper shim:** the canvas renders sections directly from their annotated-HTML source (§7.3), the same source the compiler serializes, so canvas and compiled markup agree by construction rather than by comparison. Handlebars is never parsed or executed in the browser. Ghost-sourced values are resolved by a helper shim implementing the subset the library uses: `{{#foreach}}`, `{{#get}}` (mapped to Content API queries with NQL filters), `{{img_url}}` (emitting Ghost-shaped sized URLs and `srcset`, not pass-through — NFR-6), `{{date}}`, `{{reading_time}}`, `{{#match}}`, `{{#if @member}}`, `{{navigation}}`, `{{asset}}`, `{{content}}`, `{{title}}`, `{{excerpt}}`, `{{url}}`, `{{tags}}`, `{{authors}}`, `{{t}}` (FR-Q6), pagination context, and truthy helpers — the full Appendix B surface. All Content-API values render as text nodes (NFR-3). `{{comments}}` renders a styled placeholder. Shim fidelity is enforced by contract tests asserting each shimmed helper's output matches recorded real-Ghost output for a fixed input set (NFR-6). `{{#get}}` filters may reference only template-level context, never the current render context — this constrains the section library and is binding on FR-G3's registry contract.
- **FR-H6** The `{{#get "tiers"}}`-bound surfaces (Pricing sections, the paywall, membership pages) show live tier names, prices, currency, and benefits from the connected site; sample tiers otherwise. **Tier presence never implies tier purchasability (normative).** Ghost seeds an active `$5/mo · $50/yr` "Default Product" tier at install, so `{{#get "tiers"}}` returns a paid tier carrying real prices and a real id on a site that has never connected Stripe (`research-ghost-membership-pages.md` §6). Every emitted paid CTA — tier cards, checkout buttons, `data-portal="signup/{tierId}/monthly"` — therefore compiles inside `{{#if @site.paid_members_enabled}}`, never inside a tier-count check, and every tier query filters `type:paid+visibility:public` rather than trusting the API to hide hidden tiers (§11.1, §7.6). This is the single most likely way a generated membership page ships broken. **The paywall is a template surface, not a placeable section:** its 12 designs (Appendix A §32) are selected in a standalone **Paywall editor** with its own canvas, one design active per project, and compile to `partials/content-cta.hbs` — the override point Ghost renders at the members-only cutoff the user placed in the Ghost editor. It is therefore absent from the Section Picker, from Layers and from Shuffle (FR-D5, FR-D12, FR-D13). A member ask on an ordinary canvas is an existing CTA section carrying FR-D5's member-visibility control, not a paywall. Connect (and the daily health check, FR-C5) records whether membership and paid tiers are enabled on the site; placing portal/signup sections or designing the paywall on a site with members disabled warns in the editor, and a pre-deploy check repeats it — a theme never ships dead signup forms unannounced. **The check never fires on synthesized instances**, which is moot for the paywall (the Synthesis Defaults synthesize none) and is the rule for every other case, so an untouched project is never warned about a section its user did not place.
- **FR-H7** **Context-aware binding (prevention, not warning):** the editor offers only bindings valid in the current template's render context, per the normative matrix in `appendix-b1-template-contexts.md`. Invalid bindings are never presented; there is no path by which a user can construct one. The matrix is keyed on three axes: **template** (single-resource templates such as `post.hbs`/`page.hbs` expose their resource only inside `{{#post}}`/`{{#page}}`, never at top level; list templates expose `posts` and `pagination` at the root), **scope** (top level vs inside `{{#foreach}}`), and **connected Ghost version** (fields introduced after a target's version — e.g. the seven social fields added in 6.36.0 — are not offered for that site). `@site.*` and `@member` are available in every template. Moving or duplicating a section onto another template re-validates every binding on it; bindings unavailable in the destination are surfaced at the moment of the move and must be re-pointed or reverted to static before the move completes. Ghost compiles themes without strict mode: an out-of-context binding renders an empty string with no error at build, deploy or runtime, so the editor is the only place this class of defect can be caught.
- **FR-H8** **Empty-value handling:** every bound prop compiles inside a guard; the unguarded state is unreachable. Two behaviors, chosen per binding, defaulting by kind: **text** bindings fall back to the static value the prop held before it was bound — `{{#if @site.description}}{{@site.description}}{{else}}<static>{{/if}}` — and **media** bindings hide the element they occupy, guarding the element and never the attribute. This mirrors Ghost's own themes, which substitute where a sensible alternative exists and hide only where none does. Guards use `{{#if}}` exclusively — `{{#has}}` is not a null check and reports false for numeric and boolean values. Media guards must enclose any `srcset`: an unguarded `srcset` renders a malformed attribute the browser resolves as a relative URL, producing live 404s. Every `@site` key is always defined (`null` when unset), so `{{#if @site.x}}` is sufficient in all cases.

### FR-I · Templates & Routing (routes.yaml)

- **FR-I1** Standard template set always compiled: `default.hbs` (synthesized shell: head, fonts, tokens, header/footer partials, `{{ghost_head}}`/`{{ghost_foot}}`, `{{body_class}}`), `index.hbs`, `post.hbs`, `page.hbs`, `tag.hbs`, `author.hbs`, `error.hbs` — and **where one of these has no project doc its content is synthesized per `sections-inventory.md` § Synthesis Defaults before assembly** (FR-J1), so a standard file is never emitted empty. `page.hbs` gates its title and feature-image markup on `{{#if @page.show_title_and_feature_image}}`, which Ghost's own page-builder settings drive and which gscan's `GS110-NO-MISSING-PAGE-BUILDER-USAGE` requires (FR-J6). **There is no members template family.** `members/signup.hbs`, `members/signin.hbs` and `members/account.hbs` do not exist in Ghost 6 and never render; that path is a fossil of one archived 2021 theme whose own `routes.yaml` pointed at it (`research-ghost-membership-pages.md` §1, §9, §12). A designed membership page compiles to **`custom-{name}.hbs` at the theme root** — the same file class as FR-I3's custom templates — and the user binds it to an ordinary Ghost Page by picking it from the **Template** dropdown in Ghost's page editor. **No route is emitted and none is needed:** designing a membership page adds no `routes.yaml`, and therefore removes a manual Ghost Admin step rather than adding one (FR-I4, FR-I5). Ghost stores the chosen filename on the page's own row, so the binding survives a retitle, a slug change and a theme swap. Inflozo therefore **never emits `page-{slug}.hbs`**: that form is matched against the live slug at render time, detaches silently the moment the user retitles the page, and outranks the user's explicit dropdown choice — Ghost Admin disables the dropdown outright when a slug template matches. Membership templates compile **only when the user has designed one**; untouched membership flows are served by Ghost's native Portal — no dead files ship. Removing every section from a designed membership template returns it to untouched: its file is not emitted on the next compile, and a Ghost page still pointing at that filename falls back to `page.hbs` rather than erroring. `private.hbs` follows the same conditional pattern: it compiles only when a Private Site Gate section (Appendix A §31) is designed, and so does `partials/content-cta.hbs`, which is emitted only when the paywall has been designed (FR-H6). **The emptying rule is general:** removing every section from any template returns it to untouched, and the consequence differs by class — the six synthesizable templates (`index.hbs`, `post.hbs`, `page.hbs`, `tag.hbs`, `author.hbs`, `error.hbs`) re-synthesize from the defaults on the next compile, while every conditional template stops emitting entirely. **One class does not stop:** a Routes Manager custom template that has a `routes.yaml` route pointing at it keeps emitting even when emptied, because a route whose template is missing raises `IncorrectUsageError` and the URL returns 500 (`research-ghost-membership-pages.md` §1) — removing that surface is a Routes Manager deletion (FR-I3), not an emptying. **Hiding every section is not emptying** (FR-D5): a fully hidden template is designed and emits an empty body.
- **FR-I2** **Routes Manager** (dedicated surface reachable from the editor): a visual builder for `routes.yaml` — define **collections** (URL prefix, filter, assigned template — page size is always the global `posts_per_page`, FR-Q1; Ghost has no per-collection page size) with a rich filter builder (All/Any condition groups over tag, author, primary tag/author, featured, visibility and has-feature-image) and drag-to-reorder collection precedence; **channels** (filtered post streams with their own path and RSS feed); **custom routes** (static path → custom template); and taxonomy prefixes; plus a live YAML preview pane and validation (path collisions, unknown templates, filter syntax) before save. All of this ships in v1. **The filter builder's field→NQL mappings are normative**: tag → `tag:{slug}` · author → `author:{slug}` · primary tag → `primary_tag:{slug}` · primary author → `primary_author:{slug}` · featured → `featured:true` / `featured:false` · visibility → `visibility:{public\|members\|paid}` · has-feature-image → `feature_image:-null`; All/Any groups compile to `+` and `,` with parenthesized nesting. **Published date is not offered:** NQL has no relative-date syntax, so "within the last 30 days" cannot compile into a static `routes.yaml` at all, and a fixed date silently freezes — the field is dropped rather than shipped broken. The builder emits NQL and never parses it, so validation is a round-trip over what the builder produced and no third-party NQL parser is a dependency.
- **FR-I3** Custom templates created in the Routes Manager (compiled as `custom-{name}.hbs`) appear in the template switcher as designable canvases and are also assignable to individual Ghost pages from the Ghost editor (documented). The switcher's "+ New template" is a shortcut that deep-links into this Routes Manager flow — one creation flow, two entry points. Deleting a custom template (or its route) in the Routes Manager warns when the template has designed content — the canvas is deleted with it (recoverable via undo, FR-D9) — and the switcher drops the removed template; an editor viewing it switches to Home with a notice.
- **FR-I4** `routes.yaml` is included in the theme zip, and uploading it to Ghost is a separate step the user performs in Ghost Admin (Settings → Labs). **There is no automated upload path, on any Ghost version or host:** `PUT /settings/routes/yaml` requires the `setting: edit` permission and Ghost grants integrations `settings: ['GET']`, so the guided "one more step" card (download button + Labs instructions) is the **only** upload flow and is designed as a first-class flow rather than offered as a fallback. **Verification is authoritative, not inferred:** `GET /settings/routes/yaml` needs only `setting: browse` and *is* allowlisted, so Inflozo reads the live `routes.yaml` and compares it **byte-for-byte** with the compiled routes. The card resurfaces whenever they differ — including route removals, a routeless project deploying after a routed one, and rollbacks — and clears the moment they match. FR-C5's daily health check runs the same comparison, so drift is caught between deploys, not only at one. **There is no "Routes unverified" state:** the comparison always has an answer, so no limbo state exists to design, explain or test. Deploys never silently skip routes.
- **FR-I5** Projects that never open the Routes Manager compile with Ghost's default routing (no routes.yaml surprises). **There is no exception.** Designed membership pages emit no route — they compile to `custom-{name}.hbs` and are bound from Ghost's page-editor Template dropdown (FR-I1) — so a project can ship a fully designed signup, signin and member-home page and still deploy with default routing and no `routes.yaml` at all, which is one manual Ghost Admin step fewer than a routed surface would have cost (FR-I4).

### FR-Q · Theme Settings (global config & Ghost custom settings)

- **FR-Q1** A dedicated **Theme Settings** surface (reachable from the editor, sibling to the Routes Manager) configures global theme values compiled into `package.json`: `posts_per_page` (default 12) and any future config Inflozo manages. This replaces per-section derivation — feed sections' Count controls govern only their own `{{#get}}` queries.
- **FR-Q2** **Custom settings builder:** the user defines Ghost `@custom` settings for their theme — name, type (select / boolean / color / image / text — Ghost's exact five), options, default, Ghost Admin group (Site wide / Homepage / Post), optional visibility condition on another setting — compiled into `package.json` `config.custom` and thereafter editable by the site owner in **Ghost Admin → Design settings** without redeploying. Inflozo enforces Ghost's 20-setting cap with a visible meter — **3 slots and their keys are reserved for the dark-mode built-ins (FR-Q5) in every project, Light-only included**, so user-defined settings cap at 17 and toggling dark mode on or off can never overflow the cap or collide with a built-in key; a Light-only project consequently holds three slots it never compiles, which is a deliberate trade for a uniform cap and not an oversight to be optimized away. Inflozo generates lowercase snake_case keys, validates select defaults against options, and disallows defaults on image settings (Ghost rule). **Setting keys are immutable once deployed or exported** (export mirrors deploy, FR-J12 — a manually installed exported theme has stored values to protect too) — renaming a key on a later deploy is a breaking change that would erase the site owner's stored value, so the builder treats keys as permanent identifiers (rename changes the label only). Keys are unique per project; deleting a setting warns that re-creating the same key later would resurrect the site owner's stored value.
- **FR-Q3** A custom setting takes effect by **binding**, and its Ghost type follows from what is promoted — all five types are available: section controls flagged "expose to Ghost Admin" (**Toggle → boolean** · **Segmented / Named Select / Layout Picker → select** · **Image Picker → image** · **text prop → text** — Ghost Admin text settings are plain strings, so binding a text prop shows an upfront confirm: "This text won't support formatting while it's editable in Ghost Admin — bold, italic, underline, and links will be removed and disabled." On confirm, any existing inline marks are stripped and inline formatting is disabled for that prop for as long as the binding exists; removing the binding re-enables formatting) and the Style Pack accent token (**accent → color**; color promotion is accent-only in v1, FR-Q5). The compiled theme reads `{{@custom.*}}` at render time instead of the baked value for every bound control or token. Deleting, hiding, or shuffling away a section that carries a bound control warns about the binding; compile validation rejects dangling bindings (the setting must be re-bound or removed), so a theme never ships dead Ghost Admin settings or unread `{{@custom.*}}` values. **Promotion is visible and warned at pack switch:** a promoted value compiles as the Ghost Admin *default* and Ghost keeps whatever the site owner stored, so switching Style Packs (FR-E2) restyles the canvas while the live site keeps the owner's old accent. The Style panel shows which tokens are promoted, and switching packs while the accent is promoted warns before the switch lands.
- **FR-Q4** The canvas previews custom settings at their defaults; compile validation + gscan cover the generated custom config.
- **FR-Q5** **Dark-mode built-ins:** Light+Dark projects always compile three built-in custom settings — `color_scheme` (Auto/Light/Dark — Auto follows the visitor's system preference in pure CSS, FR-E4; Light/Dark pin a mode), **Dark accent color** (color; default = the pack's hand-paired dark accent), and **Dark logo** (image; falls back to the light logo when unset) — leaving 17 slots for user-defined settings. The three built-in slots and keys are reserved in every project — Light-only projects simply don't compile them (FR-Q2) — so switching modes never overflows the cap. Color promotion is **accent-only in v1** (FR-Q3): promoting the accent creates the *light* setting, and its dark counterpart — the Dark accent built-in — already exists, so both modes stay owner-controllable as a pair. In a **Light-only** project the accent promotes as a single light setting: no dark counterpart exists and none is needed, so promotion is permitted there on the same terms. Other pack tokens have no dark built-in counterpart and are not promotable (deferred: Appendix G). Promoting the accent shows a one-time caution ("once this lives in Ghost Admin, contrast is in your hands" — AA cannot be re-validated post-deploy). Promoted colors compile as an inline token block in `default.hbs` (runtime values cannot live in static CSS).
- **FR-Q6** **Translations module:** every compiler-generated, visitor-facing **chrome string** — labels that are not user-editable text props: pagination ("Older posts", "Newer posts", "Page {page} of {pages}"), load-more/infinite-scroll labels, member form feedback (success/error/confirmation), error-page copy, search trigger and placeholder text, skip-link, lightbox/gallery labels, "Read more"-type card labels — lives in one **standard string catalog**, authored normatively in `appendix-h1-string-catalog.md` with a stable key and an English default per string. **Keys are dotted `namespace.name`, never the English string itself**, so improving a default never renames a key and never orphans a user's override. `.hbs` output consumes catalog strings **exclusively via Ghost's `{{t}}`** with `{placeholder}` hash params — never hard-coded literals — and compile validation enforces it. **Strings written by bundled JS are out of `{{t}}`'s reach**, because Ghost never runs `assets/js/main.js` through Handlebars: those keys are resolved at compile time (defaults plus overrides) and emitted as **`data-i18n-*` attributes on their module's mount element** (FR-J4), which validation asserts instead; the `{{t}}`-only rule is scoped to `.hbs` output explicitly. **`credit.*` is a locked namespace:** the "Built with Inflozo" strings live in the catalog so they compile through the same path, but they are **not listed in the Translations surface and are not overridable on any plan** — whether the credit *appears* is the plan question (FR-J15); what it *says* is not a question, and an override reaching the compiler for a `credit.*` key fails the build rather than being silently dropped. A dedicated **Translations** surface (sibling to Theme Settings, FR-Q1) lists the overridable catalog with English defaults and lets the user override any label, in any language. **The theme ships exactly one locale file**, named for the project's language and carrying the whole catalog — English defaults with the user's overrides applied over them — so every key always resolves and no second file can disagree with it; when the project language is English that single file *is* `en.json`. **Language is stored on the project**, defaulted from the connected site's `@site.locale` at first link and always user-editable; switching the project to a site whose locale differs warns before the switch, because the overrides were written in the old language. **Catalog keys sit inside FR-J14's backward-compatibility contract:** append-only, never reworded in place, and a superseded key ships a migration map that carries the user's override forward. **RTL is not supported in v1** (Appendix G): selecting an RTL language code — or linking a site whose `@site.locale` is one — requires a blocking acknowledgement that generated themes are LTR-only, recorded and repeated as a pre-deploy warning. **Scope limit, stated plainly:** strings inside Ghost's own surfaces — Portal, native comments, and the Sodo search overlay — belong to Ghost's i18n namespaces and cannot be reached by a theme catalog; the catalog covers the theme-rendered search *trigger* and placeholder only. The canvas renders the user's overridden strings via the `{{t}}` shim (FR-H5); ZIP export includes the locale file.

### FR-J · Theme Compiler & Deploy

#### Compile

- **FR-J1** Compiler input: project doc (per-template ordered section instances with content values, control values, dark overrides) + Style Pack + routes config + referenced assets. **Templates with no doc are synthesized per `sections-inventory.md` § Synthesis Defaults before assembly** (FR-I1) — an untouched template has no doc at all, so without this step the compiler emits nothing for it and the Synthesis Defaults are specification-only. **Mechanism (mandated; empirically validated by `spike-compiler/`):** sections are authored as annotated HTML; the compiler walks the DOM, substitutes content and control values, injects Handlebars block helpers as HTML comment markers, serializes with `outerHTML`, and resolves markers and expression tokens in a final pass. Handlebars is never parsed, evaluated or printed anywhere in the product — there is no partial evaluator and no AST printer. Two mechanics are binding on the implementation, both discovered in the spike: Handlebars expressions are carried through serialization as **opaque ASCII tokens** swapped back afterwards, so expressions containing quotes survive intact inside attributes; and **comment-wrapped markers are unwrapped before token substitution**, because substituting first makes a marker Inflozo inserted indistinguishable from a comment a section author wrote. **User content is emitted inert:** any Handlebars syntax a user types into a text prop (`{{title}}`, `{{{x}}}`) is escaped so it renders as literal characters and is never interpreted by Ghost. **Output quality is a requirement, not a by-product** — the generated theme must be hand-editable and production grade, at Casper/Source quality: repeating markup whose content comes from **Ghost** (post cards, pagination, bylines, subscribe forms) is extracted into real partials invoked with **no parameters**, because `{{#foreach}}` supplies the context, while markup whose content comes from the **design** is inlined and baked; class names derive from section names; one organized stylesheet carries the tokens at its top; section boundaries carry comments; `package.json` is complete; everything is Prettier-formatted; and no builder fingerprints appear anywhere in the output. Output: a complete Ghost 5.x/6.x-compatible theme matching the structure in §7.4, emitting **no `engines.ghost-api` key** — gscan carries `GS010-PJ-GHOST-API-PRESENT` as a standing *warning* on both the v5 and v6 specs, so emitting it would guarantee a warning on every compile against FR-J6's 0/0 target; compatibility comes from the helper surface the library uses, not from a `package.json` declaration (NFR-7).
- **FR-J2** `package.json`: project-derived name/description/version; `card_assets: true`; standard `image_sizes` map; `posts_per_page` from Theme Settings (FR-Q1); `custom` = the dark-mode built-ins (FR-Q5, Light+Dark projects) plus any user-defined custom settings from FR-Q2 (cap-enforced, P3).
- **FR-J3** Assets: only assets actually referenced by the project are copied into `assets/images/` with content-hashed filenames, **each emitted as a fixed rendition set — 400 / 800 / 1600 px wide plus the original** — so FR-J5's `srcset` has real files behind it rather than a promise. Fonts are **self-hosted**: the compiler bundles woff2 subsets of the project's font pairing (from the curated ~30-pairing pool, FR-E1) into `assets/fonts/` with `@font-face` and `font-display: swap`. **Subsetting is static, by script range, never content-driven** — the theme renders posts written after deploy, which the compiler cannot see: latin + latin-ext by default, and a project whose language (FR-Q6) falls outside that range ships the **full face** for the covering script, with the size consequence surfaced in the budget below rather than silently absorbed. Generated themes make no third-party font requests (Google Fonts hotlinking is a documented GDPR liability for EU site owners, and a runtime dependency P5 forbids). Section CSS is emitted only for placed sections; global CSS = token block + base/reset + shared primitives + `cards.css` (Koenig treatment per Appendix A §33). **A theme-size budget is enforced and surfaced pre-deploy** — total zip, per-entry and uncompressed total — because Ghost rejects oversized uploads with `COMPRESSED_TOO_LARGE`, `ENTRY_TOO_LARGE` and `TOTAL_TOO_LARGE` at host-configured limits (Ghost(Pro) Starter is separately documented at 5 MB). The real limits are probed on the §4 targets and the budget is set below the lowest observed; a project over budget is told which assets are responsible **before** it attempts a deploy.
- **FR-J4** JS: behavior modules bundled only if used (mobile nav, load-more, infinite scroll, marquee, accordion, lightbox, TOC scroll-spy, count-up, mode toggle, **and the A23 Custom Overlay search client** — a client-side Content API query with result rendering, which NFR-2's JS budget counts). Vanilla JS, no framework, deferred. Every module carries its FR-Q6 strings as `data-i18n-*` attributes on its mount element; no module contains a visitor-facing literal.
- **FR-J5** Generated markup follows Ghost theme requirements: `{{ghost_head}}`/`{{ghost_foot}}`, `{{body_class}}`, `{{post_class}}`, no deprecated helpers, `{{img_url}}` with `srcset` + WebP + lazy loading below the fold for Ghost-hosted content images (theme-bundled assets ship pre-generated responsive sizes from compile), portal `data-portal` attributes, paywall via the `content-cta.hbs` partial Ghost renders at the members-only cutoff (FR-H6); all chrome strings emit via `{{t}}` against the shipped `locales/` files (FR-Q6) — no hard-coded visitor-facing literals.
- **FR-J6** **gscan gate:** every compile runs gscan server-side. Errors block deploy with human-readable mapping; warnings are surfaced but deployable. Target for all library output: **0 errors, 0 warnings** — reachable, and confirmed empirically by `spike-compiler/` against both the v5 and v6 specs, once FR-J1 omits `engines.ghost-api` and FR-I1 gates `page.hbs` on `@page.show_title_and_feature_image`. **Version policy:** Inflozo pins one gscan version, at or above the newest version bundled by any supported Ghost target, so a theme passing Inflozo's gate is not rejected by the target's own gate on upload; a gscan upgrade lands only behind a library release with a full re-run of the whole inventory, never silently, because a bump can turn the shipped library red and block every user's deploy at once. **The human-readable mapping is scoped to the reachable shortlist** — the rules Inflozo's own output can actually trip, not gscan's full ~100 — and any unmapped rule falls back to a stated verbatim format (rule code, gscan's own message, the file, and a docs link), so no compile ever surfaces a raw stack trace.
- **FR-J7** Artifacts: each successful compile stores the zip in a `deploy-artifacts` bucket (excluded from the user's asset quota). Retention: last 10 per project (Pro) / last 3 (Free).

#### Deploy & rollback

- **FR-J8** Deploy: server-side upload to the site's Admin API (themes upload endpoint) with optional **Activate** (owner requirement: "deploy only" vs "deploy and activate" are distinct buttons). Progress UI: Compiling → Checking (gscan) → Uploading → (Activating) → Live, with friendly error surfacing (auth failed → reconnect CTA; version mismatch; Starter-plan block per FR-C2). Cancel is available during Compiling/Checking; once Uploading starts, the deploy runs to completion (idempotent; rollback covers regret).
- **FR-J9** **Rollback:** deploy history per project×site lists version, timestamp, gscan summary, active badge; any retained artifact redeploys in one click. Rollback is exempt from FR-L3's Pro exit gating — restoring an artifact that already ran is always allowed, on any plan. Rollback and snapshot restore (FR-J13) redeploy stored artifacts, not the working document, so they never require the edit lock (FR-D18).
- **FR-J10** Theme naming: `inflozo-{project-slug}`, auto-incremented semver per deploy; version shown in Ghost Admin and the history list. **The theme name freezes per site, at the project's first deploy to that site** — each site gets its own frozen name, and deploying the project to a different site later freezes a fresh name there. Renaming the project afterwards changes its display name in Inflozo only, so renames never orphan old themes in Ghost Admin and rollback history stays coherent per site. **Uniqueness is scoped to what Inflozo can actually know.** Ghost blocks `GET /themes/` for Custom Integration tokens, so Inflozo cannot enumerate a site's installed themes; whether the Owner's Staff Access Token lifts that block is a §7.6 verify-at-build item, and until it is confirmed the frozen name is tracked in Inflozo's own per-project×site binding record — which is exempt from FR-J7's artifact pruning, so pruning can never lose it and re-derive a fresh name. A collision between two Inflozo projects on one site auto-resolves with a slug suffix (e.g. `inflozo-blog-2`), surfaced to the user, and never deadlocks on the frozen name. A collision with a theme Inflozo did not deploy cannot be detected in advance and Ghost would overwrite rather than error; the `inflozo-` prefix makes it vanishingly unlikely, and the first-deploy confirmation names the exact theme that will be created so the user can catch it.
- **FR-J11** Deploys are rate-limited (10/hour per site) and idempotent; a failed upload never leaves a partially active theme. **Deploy + activate holds a per-site advisory lock**, so two projects targeting the same site serialize rather than interleave — theme activation is globally stateful and a rate limit is not a mutex. **The §4 test targets are exempt from the rate limit:** a single DoD run is 30 serialized deploys, which the limit alone would stretch past three hours before compile time, and every re-run would pay it again.

#### Lifecycle

- **FR-J12** **Theme ZIP export (all plans):** any project can download its compiled theme zip, Free included — **including a project that is read-only because the account is over its Free project cap** (FR-L3): read-only means not editable, never locked in. Projects containing Pro sections on a Free account are blocked per FR-L3's exit rule. Export gating mirrors deploy gating exactly. **Every export is recorded** (project, version, timestamp), because FR-Q2 freezes custom-setting keys "once deployed **or exported**" and that rule needs a fact to test against.
- **FR-J13** **Pre-Inflozo snapshot ("safe installs"):** at Inflozo's first theme upload to a site (deploy-only included — manual activation in Ghost Admin must not bypass the safety net), download and archive the currently active theme as a restorable artifact (excluded from asset quota, exempt from history-retention pruning). **Capture is real, not best-effort.** Ghost's `tokenPermissionCheck` allowlists only `themes: ['POST','PUT']` for Custom Integration tokens, so every `GET /themes/*` call made with an Admin API key returns 403 — on every Ghost version and every host, self-hosted 5.x, 6.x and Ghost(Pro) alike. Inflozo therefore reads the live theme with the site **Owner's Staff Access Token** (FR-C1), which that allowlist does not bind. A **pre-deploy gate** before the first deploy to a site asks the user to confirm they hold their own copy of the current theme and `routes.yaml`, and offers both as downloads: the snapshot is Inflozo's safety net, not the user's only one. Where the Staff token is absent or revoked the degraded path is a **designed flow, not a warning toast** — before activation the user is told no snapshot could be captured, and that Ghost retains the previous theme under Settings → Design, with guidance to reactivate it there. **Restore scope is signature-gated on the `package.json` marker, not the theme name.** Every Inflozo-built theme carries an `inflozo-*` name **and** a `package.json` marker, and the marker alone governs the rule: a user can export a theme, rename its package and install it manually (FR-J12), so keying on the name would let Inflozo capture its own theme as that site's "original" and turn restore-to-original into restore-to-Inflozo. A theme carrying the marker is **never** captured as a snapshot. Rollback and automated restore are guaranteed for Inflozo-signed themes (rebuilt from Inflozo's own stored artifacts, no download endpoint needed); a third-party active theme is archived and otherwise never touched. Restoring a snapshot is a one-click redeploy that skips *Inflozo's* gscan gate — but **Ghost validates every upload with its own gscan**, so an old Casper fork or a marketplace theme installed years ago on a since-upgraded site can be rejected on the way back in. That case has a designed fallback too: Inflozo offers the snapshot zip as a download and points the user at Settings → Design, where Ghost still holds the previous theme. Snapshots are stored per **site record id** (FR-C6), survive project deletion and disconnect/reconnect, and are offered as a download before account purge (FR-A5).
- **FR-J14** **Library updates & redeploy:** the section library and Style Packs are versioned with Ghost compatibility in mind. When the library advances beyond what a project's last deploy used — **each deploy records its library version and the variant manifest it shipped (FR-G3)**, which is what makes "advanced beyond" a fact rather than a guess — the project shows an "Updates available" notice with a human-readable summary of what changed, grouped by category and naming the project's affected placed sections. That summary is generated from a **machine-readable library changelog** shipped with every release: one entry per change carrying its kind (new variant · superseded variant · schema migration · catalog key · Style Pack), the ids it touches, and one line of prose. Compiles always use the current library version (a single live library, no per-project pinning — chosen for implementation simplicity); consequently **any redeploy includes all library changes since the project's last deploy** — there is no way to redeploy without them — and the canvas always renders the current library. Because the update is inseparable from the redeploy, the deploy flow makes it consensual: whenever the library has advanced since the project's last deploy, a **mandatory confirm step** lists the changes ("This deploy includes library updates: … — continue?") before compile proceeds. A live site never changes except through a user-initiated redeploy plus this confirmation; the one exemption is FR-C5's compatibility redeploy, which re-ships a design that already ran. Library releases are bound by a **backward-compatibility contract**: variants are never deleted, only superseded (hidden from the Section Picker; placed instances keep rendering); section content/control schema changes are append-only or ship a migration map applied to existing project docs; and **the string catalog is inside the contract too** — catalog keys are append-only, never reworded in place, and a superseded key ships a migration map carrying the user's override forward (FR-Q6, `appendix-h1-string-catalog.md`). Because variants are never deleted, a placed section can fail to resolve **only when a schema migration fails**: that case, and only that case, degrades to the nearest current variant — defined mechanically as the variant in the same category sharing the instance's `bindingContext` and `compileTarget` with the greatest content-schema overlap — with a visible notice. Never a silent re-render, never a failed load, and no deletion path to build. **Post-launch cadence (retention commitment):** the library keeps growing after GA on a regular cadence — target: monthly drops of new variants and/or Style Packs — delivered through this update flow; the Evergreen differentiator (§1.4) is an ongoing commitment, not a launch artifact. Because the count moves every month, user-facing copy about the library is **count-agnostic** ("hundreds of gorgeous sections"); 485 is a GA floor stated in FR-G1, never a number quoted in product microcopy (Appendix H).
- **FR-J15** **Credits & white-label:** generated themes include a "Built with Inflozo" credit in both README.md and the theme footer by default. Pro accounts can disable both per project; Free deploys and exports always retain credits. The A3 footer sections' credit toggle is this same per-project setting surfaced in context — Pro-gated, locked on for Free. If a Free design has no visible footer section, the compiler appends a minimal credit line to `default.hbs`'s footer region.
- **FR-J16** **Pre-deploy drift detection:** before every deploy after the first to a given site, Inflozo reads the live theme with the Owner's Staff Access Token (FR-J13) and compares a **content manifest** — relative path → SHA-256 of file contents, line endings normalized — against the manifest of what Inflozo last deployed there. **Zip bytes are never compared:** Ghost re-zips on download, so timestamps, entry ordering and compression differ every time and a byte comparison would report drift on every single deploy. The comparison targets the **frozen theme name for this project×site** (FR-J10), not merely whatever theme happens to be active, so a user who activated something else is not misread as having hand-edited Inflozo's. On any difference the deploy **stops** and shows exactly which files changed, were added or were removed — named by the user's own layer names wherever a file is a section partial, never by raw paths — and offers to download the live theme before overwriting it. **The check fails open:** a revoked token, a network failure, a missing theme or a 403 reports "couldn't verify" and the deploy proceeds; drift is never asserted without two manifests in hand. It is skipped on the first deploy to a site, where there is nothing of Inflozo's to compare against. The requirement is **zero false positives**, which binds the compiler as much as the check: a rename in Layers is a real change and is reported as one, and conversely **a compiled filename must never change when the user changed nothing** — an unstable name would report drift the user did not cause and void the guarantee.

### FR-K · Asset Library

- **FR-K1** **Global per-account** library (used across all projects), grid view with search, type filter (Image/SVG/Logo), and sort (Newest/Name/Size).
- **FR-K2** Upload via drag-drop/multi-select. **Client-side optimization before upload:** raster images convert to WebP (q≈82), max long edge 2400 px, through the browser's **native `canvas.toBlob('image/webp')`** — supported by every browser inside NFR-7's floor, Safari included, since well before 16.4. A bundled encoder or server-side transcode exists **only as a runtime fallback** for a browser that reports no WebP encode support; shipping the encoder unconditionally would add ~300 KB of wasm that no supported browser needs. Input cap 10 MB/file; SVGs sanitized (script/foreignObject stripped). Original filename preserved as display name. Optimization is destructive by design — originals are not retained; the upload UI states the trade-off ("Images are optimized (WebP, max 2400 px); originals aren't stored"). No browser silently uploads an unoptimized original (acceptance criterion).
- **FR-K3** Quota metering with an always-visible meter on the library page (Free 100 MB / Pro 5 GB) and upload-time enforcement with upgrade prompt.
- **FR-K4** Per-asset usage: "Used in 3 projects" chip; deleting a used asset warns and lists affected projects (deleting replaces with a placeholder in canvases; compile blocks until resolved). **Usage is tracked in a server-side index recomputed when a project doc is upserted**, never derived by scanning every doc at render time — FR-K1's grid shows a chip per asset, and N document scans per page load does not survive contact with a real library. The index is therefore **stale by up to one cloud-sync interval** (FR-D10): a doc can reference an asset for minutes before the server learns of it. Delete accordingly **re-verifies against the client's live document** before proceeding, so the warning is never wrong in the direction that loses a user's image.
- **FR-K5** Editor delivery via Supabase Storage CDN (cached egress); at deploy, referenced assets are bundled into the zip (P5).
- **FR-K6** Asset detail actions: **Replace** (swaps the file behind the asset; every usage across all projects updates), **Copy URL**, **Download**.

### FR-L · Plans & Billing (Dodo Payments)

The same block-until-resolved pattern governs every over-limit resource — Inflozo never auto-deletes: while connections exceed the Free cap, deploys are blocked until the user disconnects down to it (each site's pre-Inflozo snapshot survives, FR-J13); an over-quota asset library goes read-only (existing files stay, uploads blocked) until the user deletes below the Free cap; retained artifacts above Free's 3 are kept but no new ones are retained. An itemized sheet lists exactly what is over and by how much. There is no dormant or frozen connection state — a connection either counts against the cap or is disconnected. Hidden sections are excluded from compilation and therefore never trigger exit gates.

## 6. Non-Functional Requirements

- **NFR-1 Performance (app):** editor time-to-interactive < 3 s (p75 of 10 timed runs, **warm**); all canvas interactions hold **60 fps** — the criterion is p95 frame time ≤ 16.7 ms with **no long task > 50 ms** across a 3-second trace of drag, reorder, Variant Shuffle and control changes; control-change render < 100 ms; persistence is local-first and asynchronous — saving must never add perceptible input latency (FR-D10's no-local-storage fallback is exempt, honestly labeled); Section Picker preview lazy rendering; dashboard LCP < 2 s. **Warm** means the app shell and section-library bundle are already in the browser HTTP cache and the Supabase session is live; a cold first visit is measured but not gated. **Reference environment:** a mid-tier laptop with 4× CPU throttle (Chrome DevTools); **stress fixture:** a 40-section template. All NFR-1 and G6 targets are pass/fail on this environment and fixture, and the gate is **manual-only** — run against the reference laptop before each release, never on CI. A shared CI runner is not that machine and 4× throttle on it is not reproducible, so a CI number would be noise presented as a gate. Beyond the fixture, graceful degradation (FR-D14).
- **NFR-2 Performance (output):** **Lighthouse is not measured.** A generated theme runs on *the user's* Ghost host, where TTFB alone can move the score 20 points on identical markup, so a host-determined number has no truth value and naming a host would gate Inflozo on infrastructure it does not own. Instead the compiler asserts, in CI and without a Ghost host, the properties Inflozo actually controls — on every compiled theme: (1) every image carries a **correct `srcset` and `sizes`** matching the rendition set it was generated with (FR-J5); (2) every shipped font is **subset, preloaded, and `woff2`-only**; (3) **no render-blocking JS** — every theme script is `defer`red or `type="module"`; (4) a **CSS budget of ≤ 50 KB gzipped per rendered template** (tokens + shared primitives + that template's section styles); (5) **no layout shift from unguarded elements** — every media binding compiles inside its FR-H8 guard, asserted by proving no unguarded `src`/`srcset` survives compilation. **JS budget: < 40 KB gzipped for a *maximal design*** — maximal design means every FR-J4 behavior module bundled **together with the A23 Custom Overlay search client** (Content API query + result rendering); a design using fewer modules ships proportionally less. Zero console errors on every template of every compiled fixture theme.
- **NFR-3 Security:** RLS on every table keyed to `auth.uid()`; Admin API keys and the Owner Staff Access Token in Supabase Vault, server-only, decrypted per request; short-lived Admin JWTs minted per call; deploy + upload rate limits; Dodo webhook signature verification; SVG sanitization on upload (FR-K2). **The canvas renders no untrusted HTML.** It reads list and metadata fields only — posts, pages, tags, authors, `@site` — and **never post or page body HTML**, which renders as dummy placeholder content instead. Every Content-API value therefore enters the DOM as a **text node, never through `innerHTML`**: there is no sanitizer library on the canvas path and none is needed, because there is no HTML to sanitize. Three carve-outs complete the rule: (1) `codeinjection_head` and `codeinjection_foot` are **never read into the canvas, rendered, stored, or logged** — FR-C2's connect-time check tests only whether they are non-empty and discards the result, which is what lets §1.2 surface its notice without the injected code ever entering Inflozo; (2) every URL-valued field is **scheme-validated (`http`/`https` only)** before it reaches an `href`, `src` or `srcset`; (3) **excerpts render text-only and are sanitized**, being the one field Ghost may return carrying markup. The canvas iframe is same-origin (§7.3). **CSP** (app and marketing): `default-src 'self'`; `script-src 'self'` — **no `'unsafe-eval'`**, which nothing needs because Handlebars is never parsed or executed in the browser (FR-H5); `style-src 'self' 'unsafe-inline'`; `img-src 'self' https: data: blob:`; `connect-src 'self'` plus the Supabase project origin and the connected Ghost site's origin (client-side Content API reads — P5); `frame-ancestors 'none'`; `base-uri 'none'`; `object-src 'none'`; `form-action 'self'`.
- **NFR-4 Reliability:** autosave offline queue with retry/backoff; deploys idempotent with immutable artifacts; background site health checks; Supabase spend-cap alarms and usage dashboards; Supabase Postgres point-in-time recovery (PITR) enabled for user work-product, with a restore drill exercised before launch.
- **NFR-5 Accessibility:** tool **axe-core**, ruleset **WCAG 2.1 AA**, threshold **zero violations** — pass/fail, no score. Scope: **all 485 shipped variants and the Inflozo app itself.** Variant scanning runs on the NFR-6(a) render matrix, against the same renders, at near-zero marginal cost — no second matrix exists. Generated themes carry an alt attribute on **every** image (user-supplied, falling back to the bound Ghost field) and a correct heading order per template. The app is keyboard-complete: reorder via keyboard, focus management in overlays and **across the canvas iframe boundary** (§7.3), reduced-motion support. User Style Pack token edits can still break contrast — FR-E3's color picker runs a **live contrast check** and warns before the edit lands, and responsibility transfers to the user at that point (a warning, never a block).
- **NFR-6 Quality automation:**
  - **(a) Render matrix** — every section variant × 3 reference Style Packs × light/dark × 3 viewports → Playwright screenshot baselines with diff gates (8,730 renders per run). **Threshold:** a variant fails above **1% differing pixels** at a per-pixel tolerance of 0.1. **Pinned renderer:** one fixed Playwright/Chromium version in one fixed container image with fonts installed in the image, animations and caret disabled — the runner is part of the baseline. **Baseline regeneration:** a change to a Style Pack, a shared primitive or the pinned renderer invalidates the whole set at once, so a mass rebaseline requires the owner's approval on a sampled visual review (one variant per category, both modes), lands as its own commit touching baselines only, and names the change that caused it. The NFR-5 axe-core scan runs on these same renders.
  - **(b) Compile CI** — nightly assembly of synthetic themes covering 100% of variants → gscan 0/0.
  - **(c) Fidelity, in three layers.** There is no DOM-normalized golden diff: it could only pass by normalizing away the image URLs FR-J5 depends on, which would blind the one test that underwrites the WYSIWYG promise. **(c1) Compiled-output snapshots** — the `.hbs` each variant compiles to is committed and diffed **per-commit**, so any change to emitted theme code is visible in review. **(c2) Shim contract tests** — every shimmed Ghost helper (FR-H5, Appendix B) is asserted against **recorded real-Ghost output** for a recorded input set, per-commit and offline; image URLs are compared, not normalized away, because the canvas shim emits Ghost-shaped sized URLs and `srcset` rather than passing paths through. **(c3) Nightly perceptual diff** — the canvas rendered against the same page deployed to a real Ghost target (§4), at (a)'s threshold and on (a)'s pinned renderer.
  - **(d) E2E** — Playwright against the running stack (pre-launch: production, per §4's mandate; post-launch: the Test environment, §4) covering: auth, connect, build, shuffle, dark authoring, deploy to all Ghost deploy targets (§4), rollback, billing (Dodo test mode), quotas.

  Only **(c3)** and **(d)** touch a real Ghost.
- **NFR-7 Compatibility:** evergreen Chrome/Edge/Firefox + Safari 16.4+; generated themes support Ghost 5.x **and** 6.x — compatibility comes from the **helper surface the library uses** (Appendix B), verified by gscan against the v6 spec and by the NFR-6(c) fidelity layers, **not** from a `package.json` declaration: no `engines.ghost-api` key is emitted (FR-J1), because gscan flags it as a standing warning on both specs. **Ghost 5.x reached end of life in January 2026:** 5.x *connections* stay supported for lagging sites, but 5.x parity is a compatibility courtesy rather than a permanent commitment, and T3 is the first target to drop under schedule pressure (§4). Ghost 4.x and older are rejected at connect with a friendly "please update Ghost" message.
- **NFR-8 Privacy/compliance:** **GDPR export** is discharged by **Supabase's own per-user data export tooling**, run by the owner on request and delivered as a JSON + assets archive within the statutory 30 days — no in-app export surface ships in v1, and no FR specifies one. **Delete** is FR-A5. **Analytics: marketing site only** — privacy-respecting analytics may run on inflozo.com; the authenticated app ships **no analytics and no telemetry** in v1 (this is what makes G1/G2/G8–G10 manual or moderated measurements), and no third-party trackers run anywhere. Dodo handles tax as merchant of record.
- **NFR-9 Observability:** Sentry (app + server), structured deploy logs (per-stage timing, gscan output), Supabase usage alerts at 60/80/95% of included quotas.

## 7. Technical Assumptions & Architecture Direction (for the BMAD Architect)

### 7.1 Stack

- **Frontend/app:** Next.js (App Router, TypeScript) on **Vercel** — one codebase serving marketing (SSG) at **inflozo.com** and the authenticated product at **app.inflozo.com** (two domains, one deployment).
- **Backend:** **Supabase** — Postgres (+ RLS), Auth (magic link + experimental passkeys, `supabase-js` ≥ 2.105.0 pinned), Storage (buckets: `assets/{userId}/…`, `deploy-artifacts/{projectId}/…`, `site-snapshots/{userId}/{siteId}/…`, `thumbnails`), Vault for the Admin API keys **and the Owner Staff Access Token** (FR-C3).
- **Server compute:** Vercel Node.js functions (not Edge) for: compile + gscan + zip, Admin API proxy (JWT mint), Dodo webhooks, health checks and notification retention (Vercel Cron). **Thumbnail capture is not server work** — FR-B1 captures it client-side from the canvas, so no headless browser runs on Vercel and Appendix F carries no Chromium line item.
- **Compile job posture:** the compile function assembles a file tree, subsets fonts, pulls referenced assets from Storage, runs gscan and zips. Budget it as a **long-running Node function**, sized against a measured worst case — the 40-section stress fixture across every emitted template with a full asset set — not against the platform default. Set duration and memory from that measurement and state both in the architecture; if the worst case exceeds the plan's function ceiling, split the job at the **gscan boundary**, not inside deploy, so the upload stage never grows a second timeout mode. Progress and cancellation are backed by the `deploy_jobs` row (§7.5), never by function-local state — FR-J8's five-stage UI must have something to poll when the compile has already failed.
- **Payments:** Dodo Payments hosted checkout + webhooks (fee model noted in Appendix F).
- **Email:** Resend for all transactional email (FR-P); Supabase Auth SMTP routed through Resend for consistent branding.
- **Section CSS authoring format:** **plain, flat CSS** — no preprocessor, no nesting, no build step — one stylesheet per variant, authored against Style Pack custom properties (`var(--…)`) and the control-driven data-attribute selectors of §7.3, with class names derived from the section name. **Section CSS is excluded from the app's Tailwind pipeline**: it is never scanned, never purged, never touched by the app build. The two are incompatible, not merely separate — a utility class encodes its value at authoring time, so it cannot follow a Style Pack switch (FR-E2) or a per-mode token (FR-E4), and a utility-class soup is precisely what FR-J1's hand-editable, Casper/Source-grade output requirement forbids. Tailwind styles the Inflozo app; the 485 section stylesheets are library data that the compiler concatenates and prunes into `assets/css/screen.css`. They never meet.
- **Rendering:** **there is no Handlebars runtime in the browser.** Sections are annotated HTML with two renderers over one source — canvas DOM and `.hbs` text (§7.3, FR-H5) — so the app ships no template compiler, nothing calls `new Function`, and NFR-3's CSP needs no `'unsafe-eval'`. The Ghost-helpers shim (FR-H5) is a first-class package; its fidelity is held by the NFR-6(c2) shim contract tests, not by a golden DOM diff.

### 7.2 Content & data flow

- Editor → user's Ghost **Content API** directly from the browser (browser-safe key; API is read-only, cacheable; resources: posts, pages, tags, authors, tiers, settings; NQL filters, `include` params, `Accept-Version` pinned).
- Editor → Inflozo server → user's Ghost **Admin API** only for: connection validation, theme upload/activate, reading the live `routes.yaml` for drift verification (FR-I4 — there is no automated routes *upload* path on any version or host). Never from the client.
- Deployed sites: zero runtime dependence on Inflozo (P5).

### 7.3 Single-source section runtime (mandated)

**One source, two renderers.** A section variant is authored as **annotated HTML** — plain, valid HTML carrying `data-*` directives (`data-prop`, `data-prop-attr`, `data-bind`, `data-bind-attr`, `data-empty`, `data-repeat`, `data-repeat-limit`, `data-partial`) — plus one plain CSS file (§7.1), an optional JS behavior module, and its content/control schemas (FR-G3). That single source feeds **two renderers**: one produces canvas DOM, the other produces `.hbs` text. Canvas and shipped markup therefore agree **by construction**, not by comparison — byte-comparable markup is a property of the design, not something a test has to earn expression by expression. **Handlebars is never parsed, evaluated or printed anywhere in the product** — not in the browser, not on the server. There is no partial evaluator and no AST printer, and the multi-week component those would have required does not exist. `spike-compiler/` validates the whole path empirically: 16/16 renderer assertions, and a generated theme scoring **0 errors / 0 warnings** on gscan 6.4.2 against **both** the v5 and v6 specs.

**Compiler mechanics (binding on the implementation).** The theme renderer walks the DOM, substitutes content and control values, injects Handlebars constructs, and serializes with `outerHTML` — HTML's own parser and serializer stand in for the Handlebars printer Ghost does not ship. Three mechanics are binding, all proven in the spike:

1. **Handlebars expressions are carried through serialization as opaque ASCII tokens** placed in text nodes and attribute values, then swapped for the real expression *after* serialization. Without this the serializer escapes the quotes inside an attribute-borne expression, and `src="{{img_url feature_image size="m"}}"` — the single riskiest case in the design — comes out corrupt.
2. **Block helpers inject as HTML comments carrying tokens.** `{{#foreach}}` wrappers and FR-H8's `{{#if}}` guards are placed as comment siblings around the element they enclose, then unwrapped in the final pass. Guards wrap the **element**, never the attribute.
3. **Comment-wrapped markers MUST be unwrapped BEFORE token substitution.** Substituting first makes a marker Inflozo inserted indistinguishable from a comment the section author wrote, and the compiler then rewrites author comments as template code. This is an ordering constraint on the design, not an implementation detail; it belongs in the compiler's own test suite and must not be left for the implementer to rediscover.

**Escaping.** User content is data, never code. Any Handlebars syntax a user types into a text prop is emitted **inert** as `\{{`, so Ghost renders it as literal characters and never interprets it (FR-J1). Because the rich-text serializer is the only place user text becomes markup, this rule has exactly one enforcement site.

**Control → CSS.** Controls are **closed-valued** by construction: every type in Appendix C resolves to one of a declared, finite set of named values — no free text, no units, no hex outside the Style Pack (FR-F1, FR-F2). Closed values are what make **data-attribute selectors** viable, and that is the mandated mechanism: each control writes its value to a `data-{control}` attribute on the section root, and the section stylesheet selects on it (`.hero[data-media-side="right"] { … }`). Consequences the Architect should hold: a control change is a **single attribute write** on either renderer, which is what makes FR-F4's one-frame optimistic paint affordable; the compiled theme carries the chosen values as static attributes with zero runtime cost; and a control promoted to a Ghost custom setting (FR-Q3) emits `data-media-side="{{@custom.media_side}}"` with no change at all to the stylesheet. No inline styles, no generated class names, no CSS-in-JS.

**Rich text.** The engine is **raw `contenteditable`**, mapped to schema props by the same `data-*` directives — deliberately *not* ProseMirror/Lexical/Tiptap, whose own DOM inside the iframe would break the single-source guarantee outright. Storage is **text plus marks in a JSON structure** (FR-D4): a plain string plus an ordered list of `{start, end, mark, href?}` ranges over exactly the four permitted marks, never an HTML string. Two things follow. The compiler never emits unescaped user HTML through `{{{ }}}`, because there is no user HTML to emit; and FR-Q3's plain-text lock is a **truncation of the mark list**, not an HTML parse. **The compiler is the single sanitization point:** it escapes the text, then emits the mark ranges as `<strong>` / `<em>` / `<u>` / `<a>`. Paste is normalized to the same four marks on entry, which is also why the sidebar's Content field and the canvas can edit the same value.

**Focus model across the canvas iframe boundary.** Editing chrome — outlines, handles, the insertion "+", the floating mark toolbar, the Controls sidebar — sits **outside** the iframe, positioned over it from measured rects. Inline editing happens **inside** it, in the iframe document's own `contenteditable`. A single edit gesture therefore crosses the boundary twice, and two documents each hold their own focus and selection. NFR-5 requires the editor to be keyboard-complete across this boundary. **The focus order is currently unspecified and is a UX-pass deliverable.** The Architect should assume it will be specified and keep the seam addressable: the canvas must be reachable and escapable by keyboard, selection state must survive chrome taking focus, and the mark toolbar must be operable without destroying the iframe selection it acts on.

**Same-origin, on its real merits.** The canvas iframe is **same-origin** — and not because cross-origin is incapable. A cross-origin frame can measure its own rects and host its own `contenteditable`, and `postMessage` the results out; any claim otherwise is false and must not be used to defend this boundary. The decision stands on cost, not capability: synchronous rect reads and direct DOM writes with no message protocol, no serialization of every hover, drag and control change across a bridge, and one shared style and asset context for canvas and chrome. What makes it **safe** is NFR-3's text-node rule, not the frame boundary. The canvas renders **no untrusted HTML at all** — it reads list and metadata fields only, never post or page body HTML (which renders as dummy placeholder content), and every Content-API value enters the DOM as a text node, never through `innerHTML`. There is nothing to sanitize, therefore nothing the boundary would have contained. FR-N2's marketing gallery uses the same hosting model for the same reason.

**Any proposal to re-implement a section as a React preview component is rejected by this PRD.**

**The authoring format is a deliverable.** All 485 sections are authored by the dev team as project work (E9–E11), and a section file opens directly in a browser during authoring — which is most of why annotated HTML won. The `data-*` directive vocabulary is therefore **documented as a shipped internal deliverable**, not left tribal.

### 7.4 Generated theme structure

```
inflozo-{slug}/
  package.json          # NO engines.ghost-api (FR-J1, NFR-7); card_assets, image_sizes, posts_per_page, custom (FR-Q5 built-ins + FR-Q2 user settings)
  routes.yaml           # only if Routes Manager used
  default.hbs           # shell: fonts, token block link, header/footer partials, ghost_head/foot
  index.hbs  post.hbs  page.hbs  tag.hbs  author.hbs  error.hbs
  custom-{name}.hbs     # Routes Manager custom templates AND designed membership pages — theme root only (FR-I1, FR-I3)
  private.hbs           # only if a Private Site Gate section is designed (FR-I1, Appendix A §31)
  partials/
    header.hbs  footer.hbs  post-card.hbs  pagination.hbs   # site chrome + Ghost-sourced repeaters
    content-cta.hbs     # Ghost's paywall override point — only if the paywall is designed (FR-H6, FR-I1)
    sections/
      {template}/…      # one partial per placed section, per template (e.g. sections/home/hero.hbs)
      shared/…          # sections placed on more than one template
  locales/{language}.json   # exactly one file, named for the project language (FR-Q6)
  assets/fonts/…        # self-hosted woff2 subsets of the project's font pairing (FR-J3)
  assets/css/screen.css # tokens + base + used-section styles
  assets/css/cards.css  # Koenig treatment
  assets/js/main.js     # used behaviors only
  assets/images/…       # hashed, referenced assets only
  README.md             # install + routes.yaml step + credits
```

**`partials/` root holds site chrome** — header, footer, post-card, pagination — the markup that is not a placed section, or that every template shares. **`partials/content-cta.hbs` is Ghost's paywall override point:** Ghost renders it in place of its own "subscribe to keep reading" block wherever the post's paywall line falls, which is exactly why the paywall is a **template surface with its own editor** (FR-H6) rather than a placeable section.

**Partial rules (normative):**

- **One partial per placed section.** A section instance placed on a template compiles to `partials/sections/{template}/{name}.hbs` and is invoked from that template. "One partial per placed section" replaces the undefined "instance group".
- **Byte-identical sections share one partial**, hoisted to `partials/sections/shared/`. Identity is over the **emitted `.hbs` text** after content and control substitution — not over section id, not over variant id.
- **Near-identical sections may share one partial with scalar hash params** (`{{> "sections/shared/cta" heading="…"}}`), and only where every difference is a scalar value. This is an optimization the compiler may take; emitting two separate partials is always correct.
- **Arrays are NEVER flattened into numbered hash params.** `item1_title`, `item2_title` is forbidden — Handlebars hash params carry scalars, and the flattening is unreadable in exactly the output FR-J1 requires to be hand-editable. A section whose content differs by a repeated list gets its own partial. Repeaters whose content comes from **Ghost** take **no params at all**: `{{#foreach}}` supplies the context (FR-J1, proven in the spike).
- **Layer names become filenames.** The per-instance layer name (FR-D5) is slugified to the partial's filename, with a numeric suffix on collision within its directory; when byte-identical instances merge into one shared partial, it takes the first instance's name in template-then-position order. The mapping is **fully deterministic** — the same project doc compiles to the same filenames on every machine and every run — which is what makes NFR-6(c1)'s committed `.hbs` snapshots diff cleanly instead of churning on names.
- **Custom template filenames are a frozen public API — the one exception to the rule above.** Section partial names are derived from layer names and may change freely on any recompile, because nothing outside the theme references them. A `custom-{name}.hbs` filename may **never** change once deployed: Ghost stores that exact string on every page that selects it and never revalidates or repairs it, so renaming an emitted custom template silently detaches every page pointing at it, each falling back to `page.hbs` with no error at compile, upload or render (`research-ghost-membership-pages.md` §0, §2). The filename is also the label: Ghost derives the Template dropdown's entry from it by a fixed transform — hyphens to spaces, title-cased, `custom-member-home.hbs` → "Member Home" — with no override anywhere in the theme, and `package.json` declares nothing about templates. Custom templates must sit at the **theme root**; one in a subdirectory never reaches the dropdown at all.

## Appendix B — Ghost Data-Binding Catalog (normative)

What Inflozo may bind, per the Ghost Content API (Posts, Pages, Tags, Authors, Tiers, Settings) and theme template context. **The helper shim (FR-H5) must cover this surface; FR-H5's helper list is the shim's contract and governs on any difference** — this appendix catalogs the *data*, FR-H5 scopes the *shim*.

**`@site` (Settings):** title, description, logo, icon, cover_image, accent_color, url, locale, timezone, navigation[], secondary_navigation[], members_enabled, paid_members_enabled, comments_enabled. (The Content API `/settings/` response exposes the site language as **both `lang` and `locale`** — the same value under two keys. The editor and FR-Q6's language defaulting read `locale`; an implementation that reads `lang` gets the same string, and neither is a fallback for the other.)
**Post/Page:** title, slug, url, excerpt, custom_excerpt, feature_image (+ feature_image_alt, feature_image_caption), published_at, updated_at, reading_time, featured, access, visibility, primary_tag, tags[], primary_author, authors[], comment counts (via `{{comments}}` context).
**Tag:** name, slug, description, feature_image, accent_color, url, count.posts (via `include=count.posts`).
**Author:** name, slug, bio, profile_image, cover_image, website, twitter, facebook, url, count.posts.
**Tier:** name, description, type (free/paid), currency, monthly_price, yearly_price, benefits[], welcome_page_url. `include=monthly_price,yearly_price,benefits` is a **no-op** — the tiers endpoint does not accept `include` at all and the Content API adds those three relations unconditionally — so it is emitted for readability and never relied on. **Tier presence never implies purchasability:** Ghost seeds an active $5/mo paid tier at install, so every paid CTA gates on `@site.paid_members_enabled` and every tier query filters `type:paid+visibility:public` (FR-H6, `research-ghost-membership-pages.md` §6). Prices are integers in the smallest currency unit; tiers return in ascending monthly price and are never paginated.
**`@member` (live-site runtime; editor simulates via FR-D16):** null | { name, email, status: free/paid/comped, paid flag }.
**Pagination context:** page, pages, total, next, prev → drives A34.
**Portal actions (Link Picker → `data-portal`) — the verified set:** `signup` · `signin` · `account` · `account/plans` · `account/profile` · `account/newsletters` · `signup/{tierId}` · `signup/{tierId}/monthly` · `signup/{tierId}/yearly` (a direct Stripe redirect, no modal) · `support` · `recommendations`. **`upgrade` is not a Portal value** — no branch parses it and it falls through to Portal's default screen; the upgrade action is **`account/plans`**. Ghost's own Source theme ships the broken value and it must not be copied. **Signing out is not a Portal action either:** it is `data-members-signout`, a members data-attribute, not a `data-portal` value. The theme's own forms use that same `data-members-*` family — `data-members-form` (`signin` · `signup` · `subscribe`), `data-members-email`, `data-members-name`, `data-members-newsletter`, `data-members-label`, `data-members-error`, `data-members-manage-billing` — which render Inflozo's own markup rather than a Portal modal and expose state as `loading` / `success` / `error` classes on the `<form>`; that is what makes a designed signup or signin form possible at all. **The signin seam:** the form is fully themeable, but `data-members-otc` hands the one-time-code step to a Portal modal Inflozo cannot design, so it is off by default and exposed as a control. The list above is read from Portal's source — Ghost's docs publish only four of these values — and is re-verified against each Ghost minor Inflozo certifies (§7.6, `research-ghost-membership-pages.md` §4).
**`@custom` in generated themes:** the dark-mode built-ins (FR-Q5) plus user-defined settings from the Theme Settings builder (FR-Q2) — Ghost allows 5 setting types and caps themes at 20 settings; Inflozo enforces the cap with a visible meter (P3).

**Chrome strings — `{{t}}`, the catalog and `locales/` (FR-Q6).** Visitor-facing labels the compiler generates are **not** part of the data surface above: they are catalog entries, not Ghost resources. Their normative source is **`appendix-h1-string-catalog.md`** — every key, its English default, its placeholder set and its `{{t}}`-vs-`data-i18n-*` emission channel. Binding rules: `.hbs` output consumes them **exclusively** via `{{t}}` with `{placeholder}` hash params; strings written by bundled JS are resolved at compile time and emitted as `data-i18n-*` attributes on their module's mount element, because Ghost never runs `assets/js/main.js` through Handlebars. The theme ships **exactly one locale file** in `locales/`, named for the project's language and carrying the whole catalog (English defaults with the user's overrides applied over them), so every key always resolves; when the project language is English that file *is* `locales/en.json`. `credit.*` is a locked namespace — in the catalog, never listed in the Translations surface, never overridable. The canvas resolves `{{t}}` through the same shim path as every other helper (FR-H5), so a string the user overrode reads correctly on canvas before it ships.

**Template context — where a binding is legal (FR-H7).** The catalog above says what *exists*; it does not say where it is *reachable*. The normative Template Context Matrix is **`appendix-b1-template-contexts.md`**, keyed on template × scope × connected Ghost version, and it is what FR-H7 implements against: the editor offers only bindings the matrix marks available, and an invalid binding is made unavailable rather than warned about. This is prevention rather than warning because Ghost compiles without strict mode — an out-of-context binding renders an empty string with no error at build, deploy or runtime, and passes gscan. `research-ghost-binding-contexts.md` is the citation-backed evidence behind that matrix; where the two disagree the research is right and the matrix is a bug.

**Query rules:** all editor reads via Content API with NQL filters (e.g. `tag:slug`, `featured:true`), `include=tags,authors`, `limit`, `order`, pinned `Accept-Version`. `{{#get}}` in shipped themes mirrors the same filters, and — because Handlebars is synchronous while `{{#get}}` resolves asynchronously — a `{{#get}}` filter may reference **only template-level context, never the current render context** (FR-H5, FR-G3): a registry-level constraint on what the library may express. Ghost 6 removed `?limit=all` across its APIs: every list read paginates (max 100 per page) — pagination is required on 6.x and works identically on 5.x.

### D.a Emission rules (normative — these fix the bundle size, not the table)

FR-E1 requires every pairing to declare its two families, the **weights shipped**, and whether each family ships as a **variable** or a **static** face, because all three determine `@font-face` emission and theme weight. The rules below make those declarations mechanical rather than per-pairing judgment.

1. **Heading role ships roman only.** No variant in the library sets an italic heading, so a heading italic face is never emitted. A **variable** heading family emits **one** file with its `wght` axis clipped to the declared range; a **static** heading family emits one file per declared weight (the pool declares one heading weight for every static heading).
2. **Body role ships roman + italic.** FR-D4's inline marks include italic, so a body family without a true italic cannot hold the body role — synthetic obliques are not acceptable output. A **variable** body family emits **two** files (roman + italic), each clipped to `wght 400–700`. A **static** body family emits **four** (400, 700, 400 italic, 700 italic).
3. **Same family in both roles** emits the body's two files only, provided the clipped range covers the heading weights. D12, D19 and D22 are the pool's two-file pairings.
4. **Non-`wght` axes are pinned at their design defaults** at instancing time (`opsz`, `wdth`, `SOFT`, `WONK`, `YTLC`), so a variable face never carries an axis the token system cannot drive.
5. **Ceiling: ≤ 5 font files and ≤ 200 KB of font payload per compiled theme** for a latin-script project. This is Appendix D's budget; NFR-2 asserts only that every shipped font is subset, preloaded and `woff2`-only, and FR-J3's theme-size budget is what enforces the total.
6. **Self-hosted, always.** The compiler bundles the woff2 files into `assets/fonts/`, emits `@font-face` with `font-display: swap`, and preloads the two roman faces. **No generated theme makes a request to `fonts.googleapis.com` or `fonts.gstatic.com`** — hotlinking is a documented GDPR liability for EU site owners and a runtime third-party dependency P5 forbids (FR-J3).
7. **Licensing.** Every family in the pool ships under the SIL Open Font License or Apache 2.0, both of which permit redistribution inside the theme zip the user downloads and installs. A family whose license does not permit that redistribution may not enter the pool.

### D.b Subsetting (normative)

**Content-driven subsetting is wrong here and must not be implemented.** A generated theme renders posts written *after* it was deployed — text the compiler has never seen. A subset built from the glyphs present at compile time renders every later post's unseen characters as tofu on the live site, and the failure appears weeks after deploy with no error anywhere in the pipeline.

**The workable answer is static subsetting by script range.** Default emission is **`latin` + `latin-ext`**, as two `@font-face` blocks per face carrying their `unicode-range`, so the browser fetches `latin-ext` only on pages that need it. Indicative sizes for a clipped variable woff2: `latin` ≈ 15–30 KB, `latin-ext` ≈ +8–15 KB, Cyrillic ≈ +10–20 KB, Greek ≈ +5–10 KB, Vietnamese ≈ +5–10 KB.

**Reconciliation with FR-Q6's "any language".** FR-Q6 lets a user translate the chrome catalog into any language and stores the language on the project. That promise and a latin subset collide, and the resolution is stated rather than left to discovery:

- **Latin-script project languages** ship `latin` + `latin-ext`, per the default above.
- **Non-latin project languages ship the full face** for the covering script — no Inflozo-side subsetting at all — because there is no content-independent way to narrow it. The size consequence is real and surfaced, not absorbed: a Cyrillic or Greek face runs roughly 1.5–2× a latin subset, and a **CJK face is 1–5 MB per weight** with no subsetting the compiler can perform to make it small. FR-J3's pre-deploy theme-size budget is where that lands, and a CJK project is told at the language selector that font payload will dominate the theme zip.
- **Coverage is checked, not assumed.** If the selected pairing's families do not cover the project language's script, the compiler falls back to the **system font stack** for that script and the language selector says so at the moment of selection — a theme never ships a `@font-face` that cannot render its own chrome strings.
- **RTL scripts remain blocked by Appendix G's deferral**, which the FR-Q6 acknowledgement gate enforces before the font question is ever reached.

### F.2 Billing policy (owner)

**No refunds. No mid-cycle cancellation.** Cancelling stops auto-renew; access continues to the end of the paid period and then downgrades to Free, entering FR-L3's block-until-resolved flow — the user deletes over-limit projects, connections and assets themselves, and **Inflozo never auto-deletes anything, on any path.** Cancellation always completes in ≤ 3 clicks (G10's counter-metric); there are no retention dark patterns.

Two consequences are load-bearing and are not optional implementation detail:

- **Checkout collects explicit consent to immediate delivery of the digital service and an explicit waiver of the statutory withdrawal right**, recorded with the order (FR-L1). Without that record the no-refund policy is not lawfully enforceable in EU/UK markets, and the public statement of the terms is FR-N1's Refund & Cancellation page. Whether Dodo, as merchant of record, already collects this is a verify-at-build item.
- **A dispute-opened transition exists regardless of the policy.** Chargebacks happen whether or not refunds are offered, so FR-L2 moves `pro_active → free` **immediately** on a dispute rather than at period end — a disputed account must never sit `pro_active` with a full term remaining. G9's counter-metric (refund/dispute rate < 2%) is measured on this transition.

### F.5 Break-even

- **On the baseline** (F.3, before the Test environment's incremental cost): $120 ÷ $12.61 = 9.5 → **break-even ≈ 9–10 Pro subscribers** (the $110–130 band spans 8.7–10.3). This is G7's stated figure.
- **On the total permanent fixed cost** (F.3, Test included): $135 ÷ $12.61 = 10.7 → **break-even ≈ 11 Pro subscribers** (the $125–145 band spans 9.9–11.5).

The previously stated "≈ 8–9" was computed from the monthly price alone against a cost line that treated test infrastructure as temporary. Both inputs were wrong in the same direction.

### F.6 Churn and blended LTV

The no-lock-in stance is deliberate — themes work forever, export stays open — so an **export-and-cancel cohort is expected**, and it is modeled here rather than left as an instruction to model it.

**Stated assumptions:** **25% month-1 churn**, **4% steady-state monthly churn from month 2**. G10 targets steady-state churn < 5% **measured from month 2**; the month-1 spike is this appendix's number and is not counted against that target.

The two cohorts behave differently, and the billing policy (F.2) is the reason:

| Cohort | Mix | Tenure model | Expected tenure | Net/mo | LTV |
|---|---|---|---|---|---|
| Monthly | 40% | 1 month paid, then 75% continue into a 4%/mo geometric (1 ÷ 0.04 = 25 further months) | 19.75 months | $13.82 | **≈ $273** |
| Yearly | 60% | The first 12 months are **banked** — no refunds and no mid-cycle cancellation (F.2), so a month-1 export-and-cancel is a stopped renewal, not a lost term. | **Blended** | | | | **$12.61** | **≈ $359** |

Stated gross of acquisition cost — no paid-acquisition line exists in this model. **The 4% steady-state assumption is the single largest lever here**: it implies a 25-month average life for a monthly subscriber, and it is a founder estimate, not an observation. A 6% steady-state cuts blended LTV to roughly $280.

The offsetting retention levers are all value-based: post-launch library cadence (FR-J14), the per-release compatibility broadcast (FR-C5), and yearly-default checkout (FR-L1) — the last of which is exactly what makes the yearly cohort's LTV 1.5× the monthly cohort's despite netting less per month.

### F.7 Capacity-headroom scenario (not a revenue projection)

The 1,000 Free + 200 Pro shape is a **capacity-headroom scenario**: it answers "does the infrastructure hold at that population?", and nothing else. It is **not** a forecast — 200 of 1,200 is a **16.7% paid share against G9's ≥ 3% target**, more than five times the goal, and reading it as revenue would overstate the plan by the same factor.

- **As capacity:** ≈ 1,200 accounts consume ≈ $140–190/mo of infrastructure against the $135/mo permanent floor — comfortably inside Supabase Pro's included storage and egress, which is the question the scenario exists to answer.
- **At G9's actual target:** 1,000 Free implies ≈ 31 Pro, ≈ **$391/mo net** against ≈ $135/mo fixed — profitable, ~2.9× the floor, and the number to plan runway against.
- **At the scenario's shape:** 200 Pro × $12.61 = ≈ **$2,522/mo net** (not the ≈ $2,700 a monthly-only model produced).

Every behavioral and market figure in this appendix — churn, plan mix, paid share — is a **founder estimate carrying no external source**, and is enrolled in §7.6's assumed-and-unvalidated list on those terms.

## Appendix H — Voice & Microcopy Canon (normative)

Copy across app and marketing is short, warm, confident, lightly playful — easy to understand with a bit of fun (owner directive). This canon governs Inflozo's own surfaces **and** the English defaults in `appendix-h1-string-catalog.md`, which is the normative source for every compiler-generated visitor-facing string that ships inside a user's theme (FR-Q6).

Your site just got gorgeous."**; empty dashboard **"Every great site starts somewhere. Yours starts with hundreds of gorgeous sections."**; gscan step **"Checking your theme (Ghost will love it)"**.

Rules: exactly **one confetti moment** in the product — first successful deploy (respects reduced-motion); destructive and billing flows stay serious, never cutesy; errors are human and name the fix ("Ghost said no — your Admin key expired" + Reconnect CTA).

**Product copy about the library is count-agnostic.** "Hundreds of gorgeous sections" is the canonical phrasing, and no user-facing string quotes a variant total. Two reasons, and both are structural rather than stylistic: FR-J14 commits to monthly library drops, so any number baked into copy is wrong within a month of GA — 485 is a GA **floor** stated in FR-G1, never a number in microcopy — and "sections" in visitor- and user-facing copy is the loose, plural sense, while the precise units are **34 categories** and **485 variants** (Appendix I). A string that said "485 sections" would be stale *and* would conflate the two units the glossary exists to separate.

**"Live" in the success toast is the site-is-published sense**, not §4's Live *environment*. The two senses never appear in the same surface — the toast is user-facing, the environment is an internal deployment target — and the glossary names both so the collision is visible rather than latent.
