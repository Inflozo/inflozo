P0·0 · The greyed-control pattern

A control another control has switched off is greyed, with the reason as a short sentence beside it. Never hidden, and never left accepting a value it will not honour. A control that vanishes teaches nothing — the user cannot tell a rule from a bug — and one that silently ignores you is worse.

The reason is text at the control, in the panel, at the moment the control greys. It is never a tooltip, never a help icon, and never a sentence somewhere else in the panel that the user has to connect for themselves.

Greying is the visible half; the sentence is the whole point. A control that greys without saying why has only moved the confusion — the user now knows something is wrong and still cannot tell whether it is a rule or a bug. The sentence names the control that switched it off, so the user can reach the cause in one move.

This is the same shape as the Remove button rule, seen from the other side. Remove never greys because its floor is a rule about content the user owns, and a rule is explained after the click. A control switched off by another control is explained before the click, because the user cannot act on it at all. Both answers are a sentence in the panel; neither is a tooltip.

Categories cite this frame by name and draw nothing new. Where a category's own control needs the treatment, the category supplies only the sentence — the greying, the placement and the reading order are settled here. Where a category thinks it has a second never-offered control, that is a question for the owner, not a local decision.
