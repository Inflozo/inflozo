One editing context per project — across tabs, browsers and devices

The three frames escalate deliberately: a bar, then a popover, then a modal with a danger fill. The interruption grows only as the stakes do. That escalation is the design and it stands.

1 · The reader — Editor, read-only

The canvas stays fully legible; the sidebar dims to 55% so controls are visible but nothing responds. The bar names the person, not a role, and the request is a button because asking is the expected action here.

B5a

Rosa is editing this site — you are reading along. Request editing

2 · The holder — a popover, not a modal

The holder is mid-sentence. It states the sync position before asking, so handing over is not a gamble. The countdown is a no-response timer and it stops the instant the holder interacts with the popover at all, focus included — it only runs out when nobody is there, so a present holder is never hurried into a decision that loses someone else’s work. It is announced assertively, because a request that arrives silently is a request a screen-reader user answers by not answering.

4 · The takeover — B5c, and three things about it are decided

A takeover is allowed. It is not a wall. The count is edits, never operations — a Variant Shuffle is several operations and one edit, and the number appears verbatim in the string that tells a person what they lost. And the message is honest rather than reassuring: work that had not synced is genuinely gone. The losing device’s journal is cleared unconditionally on its next hydrate, there is no merge path, and orphaned edits are never recovered.

Deploy and export require the lock

From a read-only session, Ship it or Export first prompts a take-over, surfacing “X unsaved edits exist elsewhere” — so a stale cloud snapshot can never silently ship. This state is drawn on no frame and is added to B5’s family here.
