# Epic 3 Context: Sites & Connections

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

A user connects their own Ghost site with **one credential pair** — the Admin API key and the Content API key from a single Custom Integration — sees it validated for real against their Ghost, takes their brand from it in one click, and manages several sites whose health is checked daily and whose owners are emailed once when a connection breaks. The Staff Access Token is **not** asked for here: it is Epic 7's, at first deploy, so this epic ends at a connected, previewable, **partially credentialed** site, which is a first-class state and never an error. Exit: T1 and T3 connected and validated with the token absent, the partial state round-tripped through Manage keys; the Ghost(Pro) half (T4) rides to the launch gate; the deploy-error half of Preview-only is verified at the E4/E7 joint gate because no deploy exists yet.

## Requirements & Constraints

- **Connect** enters a URL, shows guided screenshotted steps to create a Custom Integration, takes the Admin and Content keys from it, and stops. An `http://` URL is warned (live-content editing needs HTTPS from the browser). The connect screen says plainly that connecting hands over the subscriber list — Ghost offers no narrower key, so informed consent is the only lever.
- **Validation is server-side** by minting the Admin JWT and calling the **authenticated `GET /admin/config/`**; `GET /admin/site/` is never used to validate (it answers 200 to any key). The Ghost `version` is reported: 5.x and 6.x accepted, **4.x and older refused with a friendly "please update Ghost"**. The Content key is verified **client-side** with a `settings` read.
- **Probes, never questions:** `hostSettings.limits.customThemes` decides Preview-only (sky, not danger — UX-DR7); its absence means self-hosted and unlimited; present-but-unreadable is the **only** path that asks which plan. Connect computes **one boolean** for head/foot code injection, shows a one-time notice, and **discards the payload**. Portal's floating-button state is read, or asked once defaulting to on, stored on the connection. The announcement bar's content, background and visibility are read on the same call for 3.4's seed. The probe sits behind the `ghostpro_preview_probe` flag row (seeded off).
- **Auto-brand** seeds accent, logo and navigation into the active project's Style Pack and switches the canvas to live content; the announcement bar is offered as a **copy** into a placed A2 section (visibility → *show to*, background → Background role), never a live binding; a consented one-click "turn Ghost's own bar off" follows, declining leaves both bars, and the card is skippable and re-runnable from the Style panel.
- **Multi-site:** Free 1, Pro 10 (`PLANS[plan].sites` in `lib/plan.ts` — Appendix F.1 governs the frames). Disconnecting never deletes projects (they fall back to sample content) or snapshots; snapshots bind to the **site record id**, a URL with no retained record gets a **new** record with no snapshot, and a record disconnected **90 days** is purged after a notice and a download offer, on its deadline whether or not the offer was taken.
- **Manage keys** shows three credentials each **present or absent with what it enables**; the token can be added or removed any time, removal degrading its three capabilities rather than disconnecting; **the URL is immutable** (a domain move is disconnect + reconnect, with the "Moved domains? … kept for 90 days" hint); no plan field.
- **Daily health check** re-validates against `/admin/config/`, re-detects version, re-runs the `customThemes` probe (Preview-only sets and clears itself), re-reads the live `routes.yaml` for drift, and re-reads Portal and announcement settings. Failure sets **"Reconnect needed"** with reason and date. The email sends **once per healthy→unhealthy transition**, is suppressed during the outage, resets on recovery, and is capped at **one per site per rolling 7 days**; a flapping site logs to notifications only. Per Ghost release, one broadcast to every account, all plans — release notes are unusable as structured data (executed), so it is an owner-authored notice; where designs are affected it is the one compatibility carve-out allowed to reach email and rides the reconnect channel.
- No nudges anywhere; Epic 1's security floor stands (RLS keyed to `auth.uid()`, no secret in `NEXT_PUBLIC_*`, per-session CSP, zero axe violations, no analytics).

## Technical Decisions

- **Two paths, never swapped (AD-10).** The Content API is read **from the browser only**, direct to the user's Ghost, with `sites.content_key` (browser-safe by Ghost's design, delivered deliberately) and `Accept-Version` pinned. The Admin API is reached **only** through `apps/web/server/ghost-admin/*` — it does not exist yet; 3.1 creates it — the single module that mints the JWT and the single place a Vault secret is decrypted. **The write allowlist is a literal in one file with a test asserting exact membership:** theme upload, theme activate, `routes.yaml` upload, and the consented announcement-bar clear. Three writes were proposed and declined (R-22) — Ghost's `accent_color` (link to it instead), `portal_button` / page creation, site `title`/`description` — because the credential is all-or-nothing and every added write widens a radius Ghost cannot narrow (executed: the stored key reads every member's email, staff, and settings, and creates posts). **Every Admin call and every Vault decryption writes `private.credential_audit`** — route, `site_id`, allowlist item, outcome; `detail` never a secret. It is the only control here that detects.
- **The JWT mint, as the probe executes it** (`tools/probe/run-verify-all.py` `jwt()`): the key is `kid:secret`; header `{alg: HS256, typ: JWT, kid}`; payload `{iat, exp: iat + 300, aud: "/admin/"}`; HMAC-SHA256 over the **hex-decoded** secret; sent as `Authorization: Ghost <jwt>` with `Accept-Version: v{major}.0`. Ghost's own ceiling is five minutes. A Staff Access Token is `id:secret` and is minted identically — raw, Ghost answers `400 Invalid token` (executed). Per request, never cached.
- **What `GET /admin/config/` answers (executed on T1 6.58.0 and T3 5.130.6, identical):** 200 with `version` for the real key; a well-formed JWT with an unknown `kid` → `401 Unknown Admin API Key` (code `UNKNOWN_ADMIN_API_KEY`); wrong secret or tampered signature → `401 Invalid token: invalid signature`. **Admin API keys never expire** — `api_keys` has no expiry column — so "your key expired" is a failure that does not exist: the user-facing cause is *regenerated or removed in Ghost Admin*, and an `Invalid token` is Inflozo's own bug, never the user's. AD-24: the envelope's `code` is Inflozo's, one row per Ghost cause, and the integration key's `GET /admin/themes/` rejection differs by major (501 on Ghost 5, 403 on Ghost 6) — fold both into one code. `settings/routes/yaml/` reads 200 with the Admin key alone, so the drift re-read needs no token.
- **`hostSettings`** is **absent** on self-hosted, both majors (executed) — absence means not Ghost(Pro). Read in source: `customThemes` is an **allowlist of theme names, not a boolean**; the probe tests Inflozo's frozen theme name (FR-J10) against it, and "present" does not mean "blocked". A real Ghost(Pro) payload is **unobserved** — ⛔ until a Starter trial (bought when E14 opens); `tools/probe/run-verify-ghostpro.py` is the one-command gate, and the flag row exists for exactly this.
- **Settings reads:** `GET /admin/settings/` answers 200 with the whole configuration to the integration key (executed); the three announcement keys — `announcement_content`, `announcement_visibility` (a JSON **string**, e.g. `"[\"visitors\"]"`), `announcement_background` — were executed with the staff token, so 3.3 confirms they appear in the integration-key payload rather than assuming it. Portal's button is the `portal_button` setting; code injection is the `codeinjection_*` pair, computed to one boolean and discarded.
- **Storage shape (AD-7).** `public.sites`: `url` (immutable, `unique (user_id, url)`), `ghost_version`, `capability` (`full` | `preview_only`) with `capability_source` (`probe` | `deploy_error` | `user_declared`), `content_key`, `credentials_present` jsonb `{content, admin, staff}`, `site_settings` jsonb + `settings_read_at`, `code_injection_notice_shown_at`, `health` (`healthy` | `unhealthy`), `last_checked_at`, `last_health_email_at`, the three `routes_*` columns, `deploy_rate_limit_exempt`, `disconnected_at`. The client may INSERT only `(id, user_id, url, title, favicon_url)` and UPDATE only `(title, favicon_url, updated_at)` — **every other column is server-asserted**, so connect is a server action writing under the service role. `private.site_credentials`: `site_id` PK cascading from `sites`, `user_id`, `admin_key_vault_ref`, `staff_token_vault_ref` (nullable — deferred and declinable), `*_rotated_at` (nothing writes them yet; 3.6 does). RLS on, no policy, in the **`private` schema PostgREST does not expose**; `credentials_present` on `sites` is the client's mirror of it. **The schema has one `url` column, and 3.2 settled the public url's home (2026-09-08): `sites.url` is the address the customer typed, normalised to an origin, and the public `url` from `GET /admin/site/` — which answers with no key at all, executed §38 — lives in `site_settings.public_url`, read at connect and daily; the card, "View site" and Deploy Live read it, falling back to `url`.** 3.2 also widened the app host's CSP to `connect-src 'self' https:` so the browser-side Content-key check reaches any customer's Ghost (`csp.ts`), and made `credentials_present` the mirror it claims to be: the connect action writes `{content, admin: false, staff}` and `store()` flips `admin` inside the same transaction that puts the key in Vault, so the flag can never claim a key the site has not got.
- **Vault, and the connection (decided by Story 3.1, 2026-09-07).** Refs are `vault.secrets(id)`; `vault.secrets` and `vault.decrypted_secrets` are granted to `service_role` only and answer **404 over PostgREST** (executed, §21j), so `supabaseAdmin()` — supabase-js over REST — writes `public.sites` but **cannot reach `private.site_credentials` or decrypt**, and a `public` RPC that decrypts for the secret key would undo the bound §21j proved (a leaked API key yields references, not credentials). **3.1 opens one direct Postgres connection** — the `postgres` driver (3.4.9), lazy, `max: 1`, `prepare: false`, `ssl: 'require'` — through Supabase's **transaction pooler** (`aws-[region].pooler.supabase.com:6543`, IPv4, the platform's serverless shape; reached from this machine in 2.1 and 2.5), read from **`SUPABASE_DB_POOLER_URL`** (one name, one meaning; in `tools/probe/.env.example`, `tools/probe/.env` and Vercel production, which the owner adds at Deploy). The connection is the `postgres` user's; a role holding only `vault` and `private` grants is owed at the next password rotation (DW-49), and verifying the pooler's certificate chain means bundling Supabase's CA (DW-50). **DW-44 is closed by 3.1** (the trigger below). It lives in `apps/web/server/ghost-admin/db.ts` and `server-wiring.test.ts` asserts that nothing else imports the driver, reads the variable, or writes `vault.` / `private.` SQL. `store` / `remove` / `call` / `fetchWithKey` in `index.ts`; the mint and `ADMIN_WRITES` in `admin-rule.ts` (pure). **DW-44 is 3.1's:** `private.drop_vault_secrets()` — `security definer`, because the purge cascade fires under GoTrue's role — on `before update or delete` of `private.site_credentials`, deleting a ref that is removed or replaced; proved in the RLS gate against a `vault` stand-in in `PRELUDE.sql`. **Story 3.1's proof was a bearer-gated verify route** (`app/api/ghost-admin/verify`, DW-48); **3.2 deleted it** and `tools/probe/run-verify-ghost-admin.py` now drives the connect wizard itself against T1 and T3, reading `private.credential_audit`, `private.site_credentials` and `vault.secrets` read-only through the pooler because PostgREST cannot see them (§21j). **DW-54** records the three proofs that left with the route — `write-denied` (E7's first allowed write), `rotated` (3.6's Manage keys) and `staff-removed` (E7's token) — which are unit contracts and RLS-gate assertions until those stories re-drive them live. Later stories **import the module** — 3.2's connect action validates with `fetchWithKey` on `GET config/` before a site row exists (audit row with a null `site_id`), writes the row, reads `GET site/` against it (audit row with the id), then `store`s; 3.5/3.6 call `remove`; E7 stores `kind: 'staff'` — and add themselves to the importer list with a reason. **3.2 is also the second `supabaseAdmin()` importer**, because every column it writes beyond `(url, title, favicon_url)` is server-asserted.
- **Never log.** No credential, no `codeinjection_*` payload, in a log, a row, a response or a render path.
- **Ghost(Pro) admin domain:** the API URL is the site's `*.ghost.io` admin domain, which can differ from the public domain (read at docs.ghost.org 2026-09-03, not executed); the public `url` is read from `GET /admin/site/` at connect and daily, and it — never the admin domain — is what the Sites card, "View site" and Deploy Live link to.
- **Crons (AD-33): two are this epic's** — daily site health and the snapshot orphan purge — each at `apps/web/app/api/cron/{name}/route.ts`, schedule in `apps/web/vercel.json`, owning epic in the header, Vercel's `CRON_SECRET` bearer compared with `timingSafeEqual` and fail-closed, `force-dynamic` + `no-store`, 500 whenever any site failed (Vercel neither retries nor alerts). Follow 2.6: the loop is a pure function over a deps interface under `node --test` so one failure never stops the rest. The orphan purge imports `drainPrefix` from `lib/storage-drain.ts` for `site-snapshots/{uid}/{siteId}/` (it refuses an empty prefix) — objects **before** rows; it is one of the five sanctioned deletion paths, add no sixth.
- **Email** is `sendEmail()` in `lib/email.ts` — one `fetch` to Resend, `RESEND_API_KEY`/`RESEND_FROM` already in Vercel production. **Notifications** are written by this epic (AD-25) into the table 1.2 created: kinds `site_health` and `ghost_compat`, `data`/`link` in a per-kind shape declared beside the enum and validated on write, `resolved_at` set by the emitter on recovery; both kinds are exempt from the 90-day prune.
- **Carried forward from Epic 2:** client → server action → service-role write; one zod schema per boundary; `{ code, message, detail?, action? }`; a migration is a new file with `SCHEMA.sql`, `RLS-TEST.sql` and the gate's copy updated in the same commit and `bash supabase/tests/run-rls-gate.sh` green, applied to the hosted database **by hand in the Deploy phase** (the direct host is IPv6-only; between Dev and Deploy the code is live before the SQL is). `supabaseAdmin()` in `lib/supabase/server.ts` is the one privileged client, three importers named in `server-wiring.test.ts`; a fourth edits that list with its reason — never a second client. Flags are read through `lib/flags.ts`'s reader pattern, per request, fail-closed; `ghostpro_preview_probe` reuses it.

## UX & Interaction Patterns

- The export is the design authority. Connect is `S2 Onboarding.dc.html` **S2b·1** (integration guide) and **S2b·2** (fields `s2b-api-url`, `s2b-admin-key`, `s2b-content-key` — three fields, no token), the same pair as a modal is **S11b**; auto-brand is **S2c** ("Nice site. Want to keep the vibe?" — Use your brand / Skip). Sites is **S11a** (health badges; the chip reads "Key regenerated Aug 15", never "expired"), **S11c** at the Free cap (ghost slot, "Free includes 1 site. Pro connects up to 10."), **S11d + B20** Manage keys (three credentials with one line each, "Not added · Add token", the URL as read-only text "Fixed for this connection", nothing to grant). **B15** is the Preview-Only Notice — sky, "Publisher or higher", the two clearing conditions (upgrade, or move to self-hosted), a Re-check plan button; **B25** the dashboard's Connected Sites Strip ("3 of 10"); **S3e + B21** the notice in notifications. The token's full-Administrator disclosure lives on D1b — Epic 7's screen, not this epic's.
- Sites with none: an **empty screen** in S3b's shape — a drawing, "One handshake and you're in.", "Connect your Ghost site — it takes about a minute.", and a centred **Connect site** that opens the connect sheet (**the owner's test of Story 3.2 amended this on 2026-09-08, finding 7 with Questions 5 and 6**; it read "the connect card **is** the whole page", and no frame draws the new screen — it is extrapolated from S3b under R-74). The full-page handshake is `/sites/connect`, where **Connect site** leads with JavaScript off. Sites carries the shell's own top bar, as Projects does — the field says "Search sites…" and matches a title or an address — and **no bell** (Story 13.4's, ruled at his Question 4). The card's own layout is his too, and DW-57 binds 3.3, 3.5 and 3.7 to it: metadata pills on one line, **Connected** just above "Checked …". The health-check spinner sits on the badge only; "Reconnect needed" shows reason and date and links to Manage keys from every instance. A control that could never act is absent, not greyed; a greyed control shows its reason in the helper caption.
- Voice: "Ghost said no — this Admin API key no longer works. It was regenerated or removed in Ghost Admin." + Reconnect; the 4.x refusal is friendly. Widths 1440 / 834 / 390, values read off the frame; one coral focus ring.
