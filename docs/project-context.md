## Inflozo

A visual site builder for Ghost CMS: users drag ready-made sections onto a canvas, the product compiles a Ghost theme and deploys it to their own Ghost site. Next.js on Vercel, Supabase, Resend, Dodo. The owner, Umang, is a solo founder and not an engineer. Planning lives in `_bmad-output/planning-artifacts/` (start at `INDEX.md`, then `HANDOVER.md`); the build steps and every prompt live in `build-sequence.md`; stories and specs live in `_bmad-output/implementation-artifacts/`; `CLAUDE.md` carries the seven standing rules and binds every session.

## Policy

- Work on `main`. There are no feature branches and no pull-request review; the pre-commit gate (`python3 tools/doc-audit.py --check`) is the only thing between a mistake and the live branch. Never push a red gate.
- **After every story phase — create, dev, review, deploy, owner test, fix, done, and any other status change — commit and push to `main` before doing anything else** (ruling R-81). The message is one line: `Story <epic>.<story> - <Phase> - <one line about the story>`, e.g. `Story 3.2 - Dev - connect wizard validates the three keys against GET /admin/config/`. Nothing else goes in the first line.
- **The review phase and the test phase run on the real infrastructure, never on mocks alone** (ruling R-82). The keys are in `tools/probe/.env` (gitignored; `tools/probe/.env.example` is the template): Supabase, Vercel, Resend, Dodo and the two Ghost test servers T1 `ghost6.inflozo.com` (6.58.0) and T3 `ghost5.inflozo.com` (5.130.6). A spec's `## Verification` names the real endpoints and sites it hit and what they returned; a review that did not touch them is not a review. Never commit a key; never print one: never `cat`, `env`, `printenv`, `set -x` or `echo $KEY` on that file — read a key only into a command's environment (`env $(grep '^GHOST6_' tools/probe/.env | xargs) python3 …`) and record every command by the key's variable name; the pre-commit hook blocks a staged line that contains a key's value.
- **Every UI story is tested by the owner on the deployed site before it is done** (ruling R-80, as amended 2026-09-04). A code review never marks a story done; Done is written by the Record prompt on the owner's word (or on the Deploy commit for a story with `owner_test: none`). The story's spec carries `## Owner's manual test`: numbered steps, each with the URL, the screen, what to do, the dummy data to type if any, and what should be seen. His findings are fixed inside that story, not by a design pass; record them under `## Owner's test findings` and set `owner_test: issues` / `passed` in the spec frontmatter.
- **Any question to the owner, in any phase, is asked in plain English with an example, numbered options, and the recommended option or combination marked (RECOMMENDED)** (ruling R-83). He reads and rules. Never present a decision as jargon and never default one that is genuinely his. Put it under `## Questions for the owner` in the spec so the story board surfaces it.
- Never edit `_bmad-output/planning-artifacts/design/claude-design-export/` — it is Claude Design's export and the design authority (ruling R-74). A story with a surface names the frame it is built from and carries a "matches the frame" acceptance criterion.
- Never edit a document marked `record` in `INDEX.md`; never hand-edit a generated file (`INDEX.md`, `BUILD-BOARD.html`, `STORY-BOARD.html`, `STEP-*-PROMPT.txt`, the `*-PROMPTS.html` pages, the two prototype folders' `.html`) — change the generator and regenerate.
- A claim about Ghost, Supabase, Vercel or Dodo is a hypothesis until executed or read in its source. Cite `MEASUREMENTS.md` or execute against T1/T3; never assert. Counts are derived, never written down.

## Where things are

- The story board — every epic and story, its status, its prompts and the owner's test script: `_bmad-output/planning-artifacts/STORY-BOARD.html`, generated by `tools/story-board.py` from `epics.md`, `implementation-artifacts/sprint-status.yaml`, the spec files and `git log` (ruling R-84). The post-commit hook regenerates the working-tree copy after every commit; the committed copy is one commit behind by construction.
- Step 6 writes `_bmad-output/planning-artifacts/epics.md`; the specs and `sprint-status.yaml` live in `_bmad-output/implementation-artifacts/`, which the documentation gate does not walk, so a story never needs a catalogue row for them.
- The hooks are tracked in `tools/hooks/` (pre-commit gate with a secret scan, commit-msg shape, post-commit board) and installed once per clone with `git config core.hooksPath tools/hooks`.
- The phase prompts a story goes through, with placeholders: `build-sequence.md` step 7 — the board copies them from there, never retypes them.
- Every story's spec carries, besides the template: `## In plain English` (three sentences a non-engineer reads), `## Owner's manual test` (for any story with a screen), and `## Questions for the owner` (only when a decision is genuinely his).
- The PRD is `prds/prd-Inflozo-2026-08-17/prd.md` (§5 FRs, §6 NFRs, §8 epics — never read whole); the architecture invariants are `architecture/architecture-Inflozo-2026-08-19/ARCHITECTURE-SPINE.md`; the UX spines are `ux-designs/ux-Inflozo-2026-09-03/EXPERIENCE.md` and `DESIGN.md`.

## Running and verifying

- `python3 tools/doc-audit.py --check` twice after adding or moving any document (its sub-tools regenerate on the first failure).
- Both prototypes rebuild with `python3 build.py` in `ux-designs/prototype/` and `python3 build-app.py` in `ux-designs/walkthrough/`; never hand-edit their emitted `.html`.
- Ghost facts: `tools/probe/run-verify-all.py` is the pattern; read-only calls unless the reset protocol in `tools/probe/RESET-PROTOCOL.md` is followed.

## Known pitfalls

- A hardcoded count in tooling has broken twice; derive membership and totals from the source, never assert them.
- A new file under `tools/`, `docs/` or `_bmad-output/planning-artifacts/` needs a row in `tools/doc-audit.py`'s catalogue, then `--generate`, or the pre-commit hook blocks the commit; never bypass the hook.
- `bmad-build` does not stop between phases on its own and the review skill sets `done` on a clean review; the team overrides in `_bmad/custom/` correct both — read them if a run behaves otherwise.
- A propagation list cannot audit itself: end every vocabulary or schema change by grepping the repository for the old name.
- Ghost Admin API keys never expire; a regenerated key returns 401 "Unknown Admin API Key". Reading the live theme needs a Staff Access Token; any staff user has one.
